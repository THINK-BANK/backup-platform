## 2. yak-ops 是什么

### 2.1 定位（原文要点）

> "Open-source data operations platform for data integration, workflow automation, data quality, and governance."
> **"Yak Ops 最早从数据集成出发，但现在它已经不再把自己定义成'给某一个执行引擎套一层 Web UI'。"**

它把数据从接入到消费的生命周期定义为一句话：**连接、同步、开发、编排、校验、服务、治理**。

```
数据源 → 数据集成 → 数据开发 → 工作流 → 数据质量 → 数据集/分析/API → 项目空间/RBAC/审计
```

### 2.2 能力矩阵（README 自述，"现在可以做什么"）

| 领域 | 能力 |
|---|---|
| 数据源 | 统一管理与复用连接、测试连通性、**读取元数据与目录信息**、插件扩展 |
| 数据集成 | 离线同步：单表 / 多表 / 脚本化配置；实时同步：**CDC 任务定义、部署与运行控制** |
| 数据开发 | 开发任务、发布与执行生命周期，SQL / Python / Shell / Java 任务插件 |
| 工作流 | 可视化定义、调度、执行实例、**节点级执行状态**与运行历史 |
| 数据质量 | 质量总览、**表监控、规则模板、质量规则、执行记录与结果查看** |
| 数据资产 | 文件、数据集、**血缘**、分析、仪表盘、大屏、数据服务 API + 运行记录 |
| 治理运维 | 项目空间、用户、部门、角色权限、操作日志、审计、通知告警 |

### 2.3 当前集成（"已实现，不是永久限制"）

- 离线同步：**Link-Up**；实时同步：**Flink CDC**（通过 Flink REST API 管理运行时）
- 数据源插件：JDBC 通用 + Doris；存储插件：Local / MinIO / HDFS
- 任务插件：SQL / Python / Shell / Java；告警插件：钉钉 + 通用 Alert SPI

### 2.4 架构分层

```
UI (React/Umi/AntD) → boot (Spring Boot)
   → 业务域（数据源/集成/开发/Job/工作流/质量/数据集/血缘/分析/服务/告警）+ 安全与项目空间
      → SPI → Plugins（数据源/存储/任务/告警）→ 数据库/存储/Link-Up/Flink CDC
```

## 3. 它的优势与特点（提炼）

### 3.1 五条产品原则（最值得学习，原文转述）

| # | 原则 | 我们的解读 |
|---|---|---|
| P1 | **控制面应该是一体的**：数据源、任务、工作流、质量检查、数据集、API、审计事件不该是彼此无关的后台页面，而是一条可理解的操作链路 | 我们已有"备份→恢复→校验→演练"链路，但**迁移/同步/对比/克隆四条线的作业模型各自为政** |
| P2 | **执行引擎应该可以替换**：平台负责产品语义、生命周期、权限、可观测、编排；引擎只负责执行 | 与我们的"引擎抽象"理念一致，但**我们的同步引擎是自研且内嵌的**（受离线约束，合理），缺的是"执行器契约"这一层接口 |
| P3 | **重要状态必须能被看见**：长任务、调度、重试、失败、运行事件、跨模块操作，不该被藏在只会显示"运行中/失败"的按钮后 | **我们最大的差距**。目前同步作业只有一层 `sync_records`，没有"尝试/重试"与"事件流" |
| P4 | **扩展应该依赖契约，而不是依赖 Fork**：数据源/存储/任务/告警通过 SPI 扩展 | 我们有 `db_adapters`（备份侧），但**同步插件没有等价的脚本式接入能力** |
| P5 | **开源本身就是产品**：不做功能受限的演示版 | 与我们的"真实执行、如实失败"同源 |

### 3.2 工程上最值得抄的三个具体设计

#### （1）作业对象三分层（来自 P3）

yak-ops 把一次执行拆成**四层对象**：

```
definition（定义，用户配的）
  └─ deployment（部署，实时任务的发布物）
       └─ execution / attempt（执行实例 / 每次尝试，支持重试）
            └─ event（细粒度事件流）
```

并且明确：**离线同步**有 `job_definition → batch_execution → job_execution → execution_event`；**工作流**有 `definition → version → schedule → execution → node_execution → node_attempt`。

这使得"重试了 3 次、第 2 次卡在哪个节点、当时的事件是什么"成为可回答的问题。

#### （2）数据质量的"规则化"

不是写死"比对行数"，而是拆成：

```
规则模板（可复用，内置/自定义） → 表监控（绑定到具体表） → 质量规则（实例）
  → 质量执行（execution） → 规则执行结果（rule_execution） → 结果查看
```

质量规则模板甚至是 `GLOBAL`（平台级模板库），业务侧只引用。

#### （3）Project Space 的边界类型学（`PROJECT_SCOPE.md`，14 节）

这是我认为**整个项目最专业的部分**，值得逐条学习：

| 设计 | 内容 |
|---|---|
| 数据归属 5 型 | `GLOBAL`（不随项目切换）/ `PROJECT_ROOT`（独立业务对象）/ `INHERITED`（继承父对象）/ `PROJECT_RUNTIME`（执行/调度/日志/事件，便于后台恢复上下文）/ `PROJECT_PROJECTION`（投影派生数据） |
| 判断原则 | "如果对象会被独立分页、后台扫描、重试、恢复或长期留存，即使能从父表反查，也优先直接保存归属" |
| 迁移三态 | `LEGACY_GLOBAL` → `PROJECT_OPTIONAL`（新增写入、旧数据回填中）→ `PROJECT_REQUIRED`（强制隔离）。**明确禁止"未迁移却伪装成已隔离"** |
| DB 迁移模板 | Expand（加 nullable 列）→ Dual Write → Backfill（分批，避免长事务）→ Index/Unique（全局唯一改项目内唯一）→ Verify → Contract（NOT NULL） |
| 错误语义 | `PROJECT_REQUIRED` 400 / `PROJECT_NOT_FOUND` 404 / `PROJECT_DISABLED` 403 / `PROJECT_FORBIDDEN` 403 / `CROSS_PROJECT_REFERENCE` 409 |
| 防枚举 | 详情接口对不属于当前项目的 ID，**统一表现为"当前项目下不存在"**，不泄露资源真实归属 |
| 验收门槛 | 8 条，含"改 URL/ID 不能读 B 的详情""异步任务重启后仍能恢复归属""前端隐藏不能作为安全实现" |
| 服务端权威 | `project_id` 来自**服务端可信上下文**，请求体中的不得覆盖；异步任务从持久化记录恢复，不依赖 ThreadLocal/Session |

## 4. AIDBM 迁移/同步现状（自查，基于当前代码）

### 4.1 数据迁移

| 项 | 现状 |
|---|---|
| 编排引擎 | `core/db_migrate.py` → `DbMigrationEngine` |
| 阶段 | `precheck`（源/目标连通、目标库自动创建、源对象统计）→ `migrate`（结构+全量一体）→ `verify`（逐表行数比对）→ `report` |
| 状态机 | `created → checking → migrating → verifying → completed / failed` |
| 执行方式 | 后台线程 + 状态/阶段实时落库，前端 3s 轮询 |
| 安全 | 密码加密存储（`_enc_secret`） |
| 表 | `db_migration_plans` |
| **并存问题** | `core/migration.py` 是**另一套**"迁移保护"三阶段（pre/mid/post 黄金副本），与 `db_migrate.py` 语义不同（保护 vs DTS 式迁移），两套并存 |

### 4.2 数据同步

| 项 | 现状 |
|---|---|
| 引擎 | `core/sync/engine.py` |
| 模式 | `full` / `incremental` / `realtime` / 离线摆渡（`core/ferry_inbox.py`） |
| 插件 | `plugins/`：base、mysql、oracle、postgresql、sqlserver、dameng（**6 个**，无金仓/MariaDB 独立插件） |
| 类型映射 | `type_mapper.py` + `type_matrix.py`（181 行，含 `_FAMILY`、`_SPECIAL_BASES`、`_INT_UPGRADE`） |
| 预检查 | `precheck.py`（`run_precheck`，含 `_ensure_target_db`、`_target_db_missing_hint`）+ `precheck_data.py` |
| 结构比对 | `schema_compare.py` |
| 实时实现 | **双轨**：默认 `_run_realtime_polling`（纯 Python 轮询 CDC，零外部依赖，适用所有已注册插件库型，位点持久化、重启续传）；仅当 `flink_config.engine="flink"` 且源为 mysql/mariadb 时走 `_run_realtime_binlog` |
| 记录 | `sync_tasks` / `sync_records` |

> **更正**：此前内部记录中"MariaDB 源实时同步被硬编码拒绝"的说法**已不适用**。当前实现为 **polling 兜底（默认，离线主力）+ 可选 flink 轨道**，与我们的离线自足约束是吻合的设计。

### 4.3 校验能力

- 迁移：逐表**行数比对**；
- 对比：`core/data_compare.py`（结构与数据比对）；
- 异构转换：`core/hetero_convert.py`（`HeteroConvert` 类）。

## 6. 吸收方案

按"投入产出 + 与产品化的契合度"排优先级。**所有条目均不改变现有离线/零安装约束。**

### P0：作业可观测分层（对应 D1、D7）——最高价值

**目标**：让"这个同步任务为什么失败、第几次重试、卡在哪一步"成为可回答的问题。

**设计**（借鉴 yak-ops 四层，裁剪为三层，避免过度设计）：

```
sync_tasks（定义，已有）
  └─ sync_runs（执行实例：一次触发 = 一条；含 trigger_type: manual/schedule/continue）
       └─ sync_attempts（尝试：重试 = 新 attempt，含 started_at/ended_at/失败原因）
            └─ sync_events（事件流：阶段进入/退出、位点推进、告警、错误）
```

要点：
- 位点（watermark / binlog file+pos）持久化到 **run 级**，重启可续传（现有 polling 已做，需统一到 run）；
- 阶段状态落到 run，进度（已读/已写/错误行数）落到 attempt；
- 前端从"一个状态按钮"升级为"阶段时间轴 + 事件列表"；
- 迁移计划（`db_migration_plans`）同步接入同一套 run/attempt/event 模型，实现 P1"控制面一体"。

**产出**：新增 `core/sync/runtime.py`（run/attempt/event 落库与查询）+ 表 3 张 + 前端阶段时间轴组件。

### P1：校验规则化（对应 D2）

**目标**：把"行数比对"升级为可配置的质量规则集。

**设计**：

```
校验规则模板（GLOBAL，内置）：行数一致 / 主键集合一致 / 抽样内容一致 /
    checksum 比对 / 空值率 / 值域范围 / 时间新鲜度
      → 校验规则实例（绑定到迁移计划或同步任务，可选参数如抽样比例）
        → 校验执行（随迁移 verify 阶段或独立触发）
          → 规则执行结果（逐条 pass/fail + 明细）
```

要点：
- 内置模板平台级维护（对应 yak-ops 的 `GLOBAL` 模板库），业务侧只引用；
- 默认规则集 = 现在的行数比对，**保证行为向后兼容**；
- 失败时给出**可读差异**（前 N 条差异样本），沿用我们"失败可读"原则。

**产出**：`core/sync/quality.py` + 表 `quality_rule_templates` / `quality_rules` / `quality_executions` / `quality_rule_results`；`db_migrate.verify` 阶段改为调用规则引擎。

### P2：同步执行器契约（对应 D3）

**目标**：让同步能力像备份侧 `db_adapters` 一样可扩展，且引擎可替换。

**设计**：
- 新增 `core/sync/contract.py`：定义 `SyncExecutor` 契约（`probe / snapshot / stream / apply / checkpoint`）；
- 现有 polling、binlog 两条轨道封装为**两个内置执行器**，通过契约注册；
- 未来若客户环境允许引入外部引擎（如 Flink CDC），作为**第三个执行器**接入，不改核心代码（这正是 yak-ops P2 原则的落地）。

> 与备份侧 `db_adapters` 的关系：备份是"脚本模板驱动"，同步是"执行器契约驱动"，二者层次不同——前者面向"我能跑命令"，后者面向"我有流式语义"。不要强行合并。

### P3：数据源连接资产化（对应 D4）

**目标**：把散落在任务里的连接信息抽成一等对象。

**设计**：
- 新增 `data_sources` 表（名称、类型、主机、端口、凭据加密引用、归属）；
- 迁移/同步/对比/克隆统一引用 `source_id`，一处修改处处生效；
- 提供"测试连通性"与"元数据发现"（列出库/表/列，供同步选表）；
- 凭据复用现有加密（对应 yak-ops 的 `DATASOURCE_MASTER_KEY` 思路，我们已有 `crypto_pool`）。

> 注意：这是**破坏性重构**，涉及所有引用连接的页面。建议新功能先走新模型，老任务保持兼容，逐步迁移（沿用 yak-ops 的"三态迁移"思路）。

### P4：错误码体系（对应 D5，与设计说明书 G4 合并）

直接借鉴其语义建模方式，建立平台错误码：

| 场景 | 状态 | 错误码 |
|---|---|---|
| 缺少必填上下文 | 400 | `PARAM_REQUIRED` |
| 资源不存在 | 404 | `RESOURCE_NOT_FOUND` |
| 跨空间/跨域引用 | 409 | `CROSS_SCOPE_REFERENCE` |
| 目标库不存在 | 400 | `TARGET_DB_MISSING`（附建库指引） |
| 引擎不支持该能力 | 400 | `CAPABILITY_UNSUPPORTED`（附支持清单） |
| 依赖/工具缺失 | 400 | `TOOL_MISSING`（附离线安装指引） |

要点：统一 `{code, message, details}` 三段式；**详情接口防枚举**（不属于当前范围时统一 `RESOURCE_NOT_FOUND`）。

### P5：项目/空间隔离（对应 D6，与设计说明书 G9 合并）——**需先决策**

**不建议全盘照搬 Project Space**。理由：我们面向单客户内网交付，多租户优先级低于 S6 架构演进。

但**其工程方法值得预先采纳**，即使暂不实现多租户：
- 新表设计时就预留归属列（对应 `PROJECT_RUNTIME` 判断原则：**会被后台扫描/重试/恢复的执行记录，直接存归属**）—— 现在加列成本几乎为零，事后加要 Backfill；
- 若将来做多租户，直接套用其 5 型归属 + 三态迁移 + Expand/Backfill/Contract 模板 + 8 条验收门槛。

## 7. 明确不吸收的部分（及理由）

| 项 | 不吸收理由 |
|---|---|
| **Flink CDC 作为实时主引擎** | 需 JDK21 + Flink 集群，与"完全离线 + 零客户端安装"根本冲突。我们已有 polling 零依赖方案，且仅在线环境才可选 flink 轨道（已实现为可选项） |
| **Link-Up 作为离线同步引擎** | 同上，引入外部执行引擎违背离线自足 |
| **数据开发（SQL/Python/Shell/Java 任务）** | 偏离灾备定位。我们已有"自定义备份/恢复脚本"覆盖脚本化诉求 |
| **仪表盘 / 大屏 / 分析 / 数据服务 API** | 属数据资产消费域，非灾备核心。我们已有运维分析与报告导出 |
| **血缘 lineage** | 数据治理范畴，投入大、与灾备链路无直接关联。若客户需要应作为独立课题立项 |
| **React/Umi/AntD + Maven + JDK21** | 与 PyInstaller 离线打包、零构建约束冲突（我们前端为 Jinja2 + 原生 JS + 试点 Preact） |
| **MySQL 8 作为强制元数据库** | 方向相反：我们要的是"SQLite 默认 + 可选 MySQL"（G1），而非强制外部数据库 |
| **项目级角色覆盖、跨项目共享、细粒度资源授权** | yak-ops 自己也在 V1 明确延后。我们多租户尚未决策，不应提前复杂化 |

## 8. 吸收后的目标架构（迁移/同步域）

```
       ┌──────────────────────── 统一作业控制面（新增）────────────────────────┐
       │  sync_tasks / db_migration_plans（定义）                              │
       │      └─ runs（执行实例）→ attempts（尝试）→ events（事件流）           │
       │  data_sources（连接资产，加密） · quality_*（校验规则集）              │
       └───────────────────────────────┬───────────────────────────────────────┘
                                       │ 执行器契约 SyncExecutor（新增）
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
       polling 执行器            binlog 执行器            外部引擎执行器（可选，未来）
       （离线主力，零依赖）      （mysql/mariadb，可选）   （如 Flink CDC，接口预留）
              └────────────────────────┼────────────────────────┘
                                       ▼
                        类型映射 type_matrix · 预检查 precheck · 结果落库
```

**关键收益**：引擎可替换（P2 原则）、状态可见（P3 原则）、校验可配（D2）、连接复用（D4），而**离线与零安装约束完全不变**。

## 9. 落地路线

| 阶段 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| 第一步 | P0 作业可观测分层（run/attempt/event） | 无 | 中：需改同步与迁移两条执行路径 |
| 第二步 | P4 错误码体系（与 G4 合并） | 无 | 低 |
| 第三步 | P1 校验规则化 | P0（结果落 attempt） | 中 |
| 第四步 | P2 同步执行器契约 | P0 | 中：抽象不当会过度设计 |
| 第五步 | P3 数据源连接资产化 | P2 | 高：破坏性重构，需三态迁移 |
| 决策后 | P5 项目空间 | 产品定位决策 | — |

**建议**：第一步与第二步可并行，且都不触碰现有备份主链路，风险可控。**先做 P0**，因为它同时是 D1（最大差距）、P3 原则（最重要）、以及后续 P1/P2 的地基。

---

## 10. 一句话结论

yak-ops 给我们最有价值的不是功能，而是三件事：**把执行状态拆层让它可看见**、**把校验从硬编码升级为规则**、**把边界用类型学和迁移三态管理起来**。这三件事都不依赖它的技术栈，且都能在保持我们"离线 + 零安装 + 真实执行"三大优势的前提下吸收。
