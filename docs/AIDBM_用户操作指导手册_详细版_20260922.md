# 第 0 章 认识 AIDBM

## 0.1 一句话说清它是什么

AIDBM 是一套**部署在你自己机房里、完全不联网**的数据保护平台：把数据库、文件、对象存储、虚拟机的备份、恢复、验证、演练、迁移、同步全部集中管理起来。

## 0.2 三条不可违背的设计铁律（决定了你该怎么用它）

**铁律一：被保护的机器上不装任何东西。**
平台通过 SSH + 数据库自带命令（`mysqldump`、`pg_dump`、`expdp`、`RMAN`、`dmrman`、`sqlcmd`…）完成备份；需要第三方工具（如 xtrabackup / mariabackup）时，平台把二进制**临时推送**到目标机临时目录，用完即删，不留进程、不留文件。
→ **对你的影响**：数据库服务器上不要安装任何备份软件；排障时也不要想到"去服务器上装个工具"。缺工具请在平台「备份插件」页处理。

**铁律二：完全离线可用。**
平台不依赖公网 PyPI、DockerHub、NTP、AI API。所有依赖（JDBC jar、JRE、Python 包、二进制工具）都随离线交付包自带。
→ **对你的影响**：运行环境无法联网下载任何东西，任何"缺组件"的问题都要通过平台自带的插件/离线包解决，而不是 `pip install`。

**铁律三：不产生假成功。**
备份失败了就是失败，不会因为"命令跑完但没输出"就报成功；物理 tar 之类的产物克隆不了就直接报不支持，不会降级成假的"克隆成功"。
→ **对你的影响**：只要你看到 success，就一定有真实产物（有大小、有 SHA256、有文件路径）；看到失败，就去「备份记录 → 日志」看真实原因，**不要跳过**。

## 0.4 一条完整的数据保护闭环（请照这个顺序建立习惯）

```
① 建立保护层   →  数据库备份 / 文件备份 / 对象存储备份  (定期产出备份)
② 记录层       →  备份记录  (每次备份都有大小/SHA256/路径/日志，可导出)
③ 验证层       →  恢复校验 + 数据对比  (证明①真的能恢复、数据真的对)
④ 恢复层       →  数据恢复 / PITR / 对象级  (真出事时的动作)
⑤ 复查层       →  恢复记录 + 巡检 + 智能告警  (事后复盘与常态监控)
⑥ 再利用层     →  克隆服务 / 数据价值挖掘  (把冷数据变成可用资产)
```

**三条使用建议（比任何功能都重要）**
1. **新建任务后必须手工点一次「备份」**，确认 success 再交给定时 —— 没跑成功的备份不算备份。
2. **至少给重要库配一条恢复校验策略** —— 没验证过的备份不算保护。
3. **恢复是覆盖操作**，先在克隆出来的副本上验证数据，再决定是否覆盖生产。

# 第 1 章 快速上手（照着做一遍，30 分钟）

## 1.1 第一步：登录

| 项 | 说明 |
|---|---|
| 入口 | 浏览器打开 `http://<平台地址>:8080/login` |
| 默认管理员 | 用户名 `admin`，密码 `admin123` |
| 输入项 | 用户名、密码，点「登 录」 |

> **安全第一件事**：登录后立刻改掉默认密码，见 1.2。

**登录不了怎么办**
- 地址/端口写错：确认平台进程在跑（服务必须带特定环境变量启动，详见运维手册 `docs/offline_ops_manual_20260917.md`）；
- 账号被停用：找管理员在「用户管理」把该用户状态改回启用；
- 忘记密码：管理员在「用户管理 → 密码」直接重置。

## 1.2 第二步：改默认密码（管理员必做）

路径：**用户管理** → 找到 `admin` 这一行 → 右侧「**密码**」按钮 → 填新密码 → 保存。

| 规则 | 说明 |
|---|---|
| 新密码长度 | ≥ 6 位 |
| 「下次登录必须修改密码」 | 勾上后该用户下次登录会被强制改密，适合给同事开账号 |

## 1.3 第三步：纳管 SSH 主机（大多数远程场景的前提）

> **什么时候需要？** 被保护的数据库/文件在**另一台机器**上时需要。平台与被保护对象**在同一台机器**时不用纳管，任务里留空即可自动走本机通道。

路径：**文件备份** 页上半区 → 右上角「**纳管主机**」按钮

| 字段 | 说明 |
|---|---|
| 主机名称 `*` | 给人看的标识，如「MySQL生产-133」 |
| 系统类型 | Linux / Windows（决定远端命令走 bash 还是 cmd） |
| 主机地址 `*` | IP 或域名 |
| 端口 | SSH 端口，默认 22 |
| 用户名 `*` | 登录账号，建议用有备份权限的专用账号 |
| 认证方式 | **密码** 或 **私钥**（私钥需粘贴 PEM 全文） |
| 密码 / 私钥 | 与认证方式对应的一项填一项 |
| 备注 | 可选 |

纳管列表列：**ID｜名称｜连接标识｜地址｜认证｜状态｜操作**
→ 建完后可以在这里一眼确认：认证方式对不对、状态是否可用。

**也可以在任务里直接填 SSH 凭据**（不想纳管时）：数据库备份任务「高级选项」里有 SSH 地址/端口/用户名/密码四个字段，「已纳管 SSH 备份机」那一栏留空就行。平台解析顺序是：**任务内 SSH 凭据 > 已纳管主机 > 本机**。

## 1.4 第四步：完成第一次数据库备份（最重要的一节）

> 目标：给一个 MySQL 库做「每天 2:00 全量备份，保留 30 天」，并立刻手工跑一次。

**Step 1**：左侧「**数据库备份**」→ 右上「**新建任务**」

**Step 2**：表单有三个 Tab —— **基本信息 / 高级选项 / 类型参数**。第一次只填「基本信息」就能跑起来。

| 字段 | 本次填什么 | 为什么 |
|---|---|---|
| 业务系统 `*` | 例如「财务系统」 | 记录、报表、筛选都按它归类 |
| 任务名称 `*` | 例如「财务-MySQL-每日全量」 | 建议含"对象+频率"，一眼看懂 |
| 数据库类型 `*` | MySQL | 十选一：MySQL / MariaDB / PostgreSQL / Oracle / kingbase(金仓) / DM(达梦) / SQL Server / Redis / MongoDB / Neo4j |
| 备份方式 `*` | 逻辑备份（推荐） | 逻辑=库自带导出命令，通用；物理=文件级，快但需工具；自定义脚本=你自己的 bash |
| 备份类型 `*` | 全量备份 | 全量 / 增量 / 组合（全量+增量） |
| 主机地址 `*` | 数据库 IP | |
| 端口 `*` | 例如 3306 | |
| 用户名 / 密码 | 库账号 | 专用备份账号，权限够导出即可 |
| 数据库/实例名 | 库名，留空=全实例 | |
| 备份文件格式 | 默认即可 | 各类型的导出格式选项 |
| 执行时间 / 调度 | `0 2 * * *` | 表示每天 02:00（5 段：分 时 日 月 周） |

**Step 3（可选）**：切到「高级选项」，把「**保留天数**」改成你要的天数（默认 30 天）。这是以后自动清理的依据，别留着不管。

**Step 4**：点「**保存**」。回到任务列表，能看到刚建的任务，列含义：

| 列 | 看什么 |
|---|---|
| ID / 业务系统 / 名称 | 任务标识 |
| 类型 | 数据库类型 |
| 备份 IP | 目标机地址 |
| 端口/库 | 端口与库名 |
| 备份类型 | 全量/增量/组合 |
| 备份模式 | 逻辑/物理/自定义 |
| 调度 | cron 或间隔 |
| 状态 | success/failed/never；**已停用**任务显示灰色徽章 |
| 上次运行 | 最近一次执行时间 |
| 操作 | **备份**（立即执行）｜编辑｜删除 |

**Step 5（必做）**：点这一行的「**备份**」按钮，立即执行一次。
→ 然后去「**备份记录**」页，确认这一次的**状态=success、大小>0**。
→ 失败的话：点该行最右侧的日志按钮，看详细日志（可一键复制给支持人员）。

**Step 6（强烈建议）**：给它配一条「恢复校验」策略（见第 11 章），让系统以后自动证明这份备份能恢复。

🎉 到这里，你已经完成了平台最核心的使用闭环。

## 1.5 第五步：认识界面通用元素

# 第 2 章 数据库备份（核心中的核心）

> 页面：「数据库备份」。页面内有两个 Tab：**备份任务**（任务列表）、**数据库类型**（各类型的支持情况/脚本模板相关说明）。
> 这一页解决：**"我的数据库要多久备份一次、备份成什么形式、留多久、能不能立刻备份一次"**。

## 2.1 页面全景

工具栏（右上）：**新建任务** ｜ **定期清理**（黄底，重要） ｜ 刷新 ｜ 导入

行操作：**备份**（立即执行一次）｜**编辑**｜**删除**

## 2.2 新建/编辑任务：基本信息 Tab（必填项已标 `*`）

## 2.4 类型参数 Tab

通常只有一个 **类型参数（JSON）** 输入框：
- 示例（MySQL）：`{"extra_args": "--set-gtid-purged=OFF"}`
- 示例（自定义脚本）：该 Tab 会切换为「备份脚本(bash) / 产物目录 / 超时秒数」等字段。

**自定义脚本模式须知**（所有数据库类型都支持）：
- 备份脚本必须把产物写到环境变量 `$PLATFORM_BACKUP_DIR` 指定的目录里，平台才会拉回并计算真实 size/SHA256；
- 平台会注入 `PLATFORM_DB_HOST/PORT/USER/PASSWORD/NAME`、`PLATFORM_BACKUP_TYPE`、`PLATFORM_BACKUP_DIR`；
- 恢复脚本同理可以得到 `PLATFORM_BACKUP_FILE`、`PLATFORM_RESTORE_DB`；
- 脚本里的通配符与变量建议 `set -e`，**结尾不要随便 `echo` 掩盖退出码**。

## 2.6 调度怎么写（cron 速查）

5 段：**分 时 日 月 周**（空格分隔）

| 表达式 | 含义 |
|---|---|
| `0 2 * * *` | 每天 02:00 |
| `30 1 * * 0` | 每周日 01:30（0=周日） |
| `0 3 1 * *` | 每月 1 号 03:00 |
| `*/30 * * * *` | 每 30 分钟 |
| `0 9,18 * * 1-5` | 工作日 09:00 与 18:00 |

也可以不用 cron，直接用「固定间隔（每隔 N 分钟）」的方式。

## 2.7 定期清理（新增能力，强烈建议了解）

**入口**：数据库备份页工具栏 → 黄色按钮「**定期清理**」

**它解决什么问题**：备份一直积累会占满磁盘，而手工删文件风险极大（删错、删了还在保留期内、账实不符）。定期清理按**每个任务自己的保留天数**自动判定，并且**永远不会清空一个任务的最后一份可用备份**。

| 配置项 | 说明 | 默认 |
|---|---|---|
| 每日自动清理 | 总开关 | 开启 |
| 清理时间（cron） | 每天几点跑 | `10 3 * * *`（每天 03:10） |
| 每任务最少保留 | **兜底份数**，低于它一律不删 | 1 份 |
| 清理后处理 | 勾选=连备份记录一起删；**不勾选=记录标记为「已清理（过期）」，保留审计轨迹** | 建议不勾选 |

**推荐操作流程**
1. 点「**扫描预览（不删数据）**」——先看清单；
2. 预览表列：**任务｜类型｜策略｜现有成功备份｜待清理｜可释放**；
3. 确认无误后再点「**立即清理**」。

**判定规则（务必理解）**
- 依据是任务的**保留天数**（默认 30 天）；
- 任务还有 `保留份数` 这个字段（部分历史任务/接口创建会带入），清理时也会按份数判定；**当前任务表单没有开放这个输入框**，需要的话由管理员通过接口设置；
- **没配保留天数的任务不会被清理**（不会被误伤）；
- 每个任务最后 N 份成功备份无条件保留（N=上面填的最少保留）；
- 预览里出现"产物已不在磁盘"的说明，代表是**幽灵记录**（文件早已被人工删掉），清理只是把账本对齐，**不会虚报释放空间**。

- 上表（策略清单）：**#｜策略名称｜保护等级｜RPO 目标｜RTO 目标｜备份方式｜状态｜已绑定任务｜操作**

|---|---|
| 策略名称 `*` | |

## 6.4 建议用法

| 等级 | 建议 RPO | 建议做法 |

| 核心 | ≤ 15 分钟，甚至 0 | 实时备份（日志流）+ 每日全量 + 复制策略 |
| 重要 | 15~60 分钟 | 每日全量 + 日内增量 |
| 一般 | 数小时 | 每日全量即可 |

# 第 8 章 实时备份 · CDC · PITR 时间轴

> 页面：「实时备份」。页内两个 Tab：**实时保护（RT / 时间轴）** 与 **CDC（变更数据捕获）**。
> 这一页解决：**"数据库能做到秒级 RPO 吗？能不能回到某个具体的一秒？"** —— 答案是可以，这里就是入口。

## 8.1 实时保护（RT）面板

**顶部**：任务选择 + 守护状态条（守护进程状态、心跳、工作线程数、tick、当前驱动）
按钮：**创建实时保护任务** ｜ **对账** ｜ **刷新** ｜ **启动** ｜ **停止** ｜ **启动守护** ｜ **立即捕获** ｜ **恢复到此刻** ｜ **跳到最新**

**恢复点表**：时间｜类型｜位点/变更｜大小｜校验｜操作
**时间轴**：可拖动的轴（起点/中点/终点刻度），下方是恢复点列表，选中某点后可「**恢复到此刻**」。

### 创建实时保护任务

| 字段 | 说明 |
|---|---|
| 任务 | 选择一个已有任务作为基础 |
| 模式 | 实时模式（如按日志流） |
| 间隔 | 捕获/封段间隔 |
| RPO | 目标 RPO |

保存后可在列表里「**启动**」，守护进程开始流式捕获数据库的日志变更，不断生成恢复点。

### 恢复到任意时刻（PITR）

1. 在时间轴上选中一个**恢复点**（或拖动时间游标到某一时刻）；
2. 点「**恢复到此刻**」；
3. 弹窗会给出目标时间点、可用的恢复链（**计划链路/缺口检查**），并让你确认目标库/目标主机信息；
4. 可以先点「**仅校验（Dry Run）**」做一次干跑（不落数据，看可行性）；
5. 确认无误后点「**确认恢复**」。

> 界面会在存在日志缺口时明确提示（计划链路上显示 gap），这时不要强行恢复，先检查日志是否被清理。

## 8.2 CDC 变更捕获面板

**流列表**：名称｜类型｜源库｜库｜状态｜事件数｜最近事件｜位点｜操作
按钮：**新建捕获流** ｜ 刷新 ｜ **CDC 能力预检查**

### 新建捕获流

字段：名称、类型、主机、端口、用户、密码、库、**要捕获的表**、用途（purpose）。
按钮：**CDC 能力预检查**（先探测该库是否具备 CDC 能力）→ **创建并启动**。

> ⚠️ **平台不做仿真降级**：如果客户端能力不足（缺必要的日志解析依赖），实时任务会**直接置为 FAILED 并写入错误日志**，而不会产出看起来成功的假数据段。

### 事件查询与应用

筛选：表、操作类型、起始位点/时间、结束位点/时间 → **查询**
结果表：时间｜操作｜表｜主键｜前镜像｜后镜像｜位点

**两大实用动作**：
- **生成 SQL**：把选中的变更事件生成可执行 SQL（预览框可查看与复制）；
- **应用到目标库**：填目标（主机/端口/用户/密码/库/类型/模式）→ 把这段变更重放到目标库，用于"追平某个时间窗口的数据"。

## 8.3 常见问题

| 现象 | 处理 |
|---|---|
| 实时任务创建后不产恢复点 | 确认任务在列表里已「启动」；检查守护状态条是否为 running；看系统日志 |
| 日志报"客户端缺失" | 参照 §7.1 安装插件；平台**不会**替你降级成仿真 |
| 达梦/金仓特殊注意 | 它们的环境变量/常量写法有差异（平台内部已适配），但仍以Capability预检查的结果为准 |
| 目标时间点太早，无可用的恢复链 | 说明全量基线+日志已不足以覆盖该时刻，需用更早的备份 |

# 第 12 章 数据对比

> 页面：「数据对比」。
> 副标题原文：**验证恢复后的备份数据与原生产库的一致性：表清单 → 行数 → 校验和（可选）→ 抽样行**
> 它解决的是恢复校验之后的那一步：**"不仅恢复了，恢复出来的数据还得是对的。"**

## 12.1 操作步骤

1. 点「**新建对比任务**」；
2. 分别填**源库**与**目标库**的连接信息：主机、端口、用户名、密码、库名；
3. 保存并开始对比；
4. 结果按四层逐级展示：
   - **表清单**：两边有哪些表（缺表会在这一步暴露）
   - **行数**：逐表行数比对
   - **校验和（可选）**：对关键表做内容级校验
   - **抽样行**：抽若干行做逐字段比对

## 12.2 典型用法

- **恢复演练当天**：恢复完成后立刻跑一次对比，作为演练通过的硬证据；
- **跨主机迁移后**：把迁移目标库和源库做一次对比；
- **怀疑某张表数据不一致**：只对关心的表跑对比，不必整库。

> 页面采用免构建的轻量前端组件，操作就是"填两端连接 → 看四层结果"，无需额外配置。

# 第 24 章 排障手册

## 24.1 通用定位路径（请严格按这个顺序）

```
现象 → 哪个页面/任务/记录？ → 备份记录「日志」看原文
     → 系统日志筛 ERROR + 该 task_id/record_id

     → 仍未解决：日志中心「导出诊断包」
```

## 24.2 常见错误对照表

| 类别 | 典型表现 | 排查与处理 |
|---|---|---|
| **凭据/权限** | Access denied、认证失败 | 编辑任务改用户名密码；Oracle/达梦/金仓注意 OS 用户与环境变量差异；确认备份账号有导出权限 |
| **工具缺失** | command not found、找不到 xxx | **备份插件**「一键安装所需」；或在任务高级选项填「备份命令所在目录」；**不要在数据库服务器上手工装软件** |
| **连接不通** | 超时、连接被重置 | 确认端口放行；远程库用纳管 SSH 主机；加失败重试次数/间隔 |
| **本机 `.my.cnf` 干扰** | 密码明明填错却"备份成功" | MySQL 客户端会读 `~/.my.cnf`，平台已用 `--no-defaults` 规避；其他自研脚本注意同样问题 |
| **磁盘满** | ENOSPC、errno 28 | 看诊断提示的"哪个路径满/还剩多少"；用定期清理 + L1→L2 下沉；清理后重跑 |
| **超时** | 大库跑到一半失败 | 执行超时设 0（不限时）、空闲超时适当放大、开**断点续传**、失败重试 2~3 次 |
| **0 字节产物** | success 但大小 0 | 权限不足/库名错/路径不可写；看日志里的 stderr 原文 |
| **实时任务不产恢复点** | 无 PITR 点 | 确认 RT 任务已「启动」、守护状态 running；看系统日志；客户端能力不足会**直接 FAILED**而非产出假数据 |
| **增量/组合不按天跑** | 调度不对 | 编辑任务确认按天勾选 + 时间，保存后以列表显示的 cron 为准 |
| **页面异常/按钮无反应** | 弹红字提示 | 记录提示内容 + 导出诊断包提交；历史上组合任务编辑问题已修复 |
| **看不到某个菜单** | 菜单缺失 | 权限不足 → 管理员到**用户管理**开角色/附加权限 |

# 第 25 章 FAQ

**Q1：需要在数据库服务器上安装 Agent 吗？**
不需要，一条铁律。平台走 SSH + 数据库自带命令；第三方临时工具推送到目标机临时目录用完即清。**无 Agent** 页可以做零残留取证，把结果给审计看。

**Q2：平台能离线运行吗？**
这是它的设计前提。不依赖公网 PyPI/DockerHub/NTP/AI API，所有依赖随离线交付包自带。

**Q3：备份存在哪里？**
默认平台本地备份根目录（按 `<类型>/<任务>_<任务名>` 归档），也可以配 MinIO(L1)/S3(L2)/本地(L3)/磁带归档(D2T) 多级目标，详见第 5 章。

**Q4：恢复到生产库危险吗？**
覆盖式操作，务必谨慎。建议先克隆到隔离环境验证，或用 PITR 的"默认还原到独立目录"能力。

**Q5：为什么有些记录显示「已清理（过期）」？**
说明产物已按该任务的保留策略被定期清理，保留了审计轨迹。**不是备份失败**。

**Q6：定期清理会不会不小心把我最后一个备份删了？**
不会。有「每任务最少保留」兜底（默认 1 份），且没配保留天数的任务不会被清理。清理前请务必先点「扫描预览」。

**Q7：保留天数和保留份数有什么区别？**
「保留天数」在任务高级选项里（默认 30 天），是主要依据；「保留份数」是任务数据里的字段（部分历史任务/接口创建会带入），**当前任务表单没有开放输入框**，需要时由管理员通过接口设置。清理时两者都会参与判定。

**Q8：组合任务/增量任务怎么配？**
备份类型选「组合（全量+增量）」，然后分别勾全量/增量的星期并填时间。

**Q9：保存后发现调度和我想的不一样怎么办？**
以列表显示的 cron 为准。由 cron 反推的按天勾选可能与你的预期不同，编辑调整后重新保存。

**Q10：为什么建议使用逻辑备份？**
通用、跨版本、可直接挑表恢复，不需要额外工具。追求恢复速度的大库可考虑物理备份（需要工具支持）。

**Q11：备份成功后 0 字节，为什么不算成功保护？**
0 字节意味着没有真实数据，属于"假成功"；平台会以大小/SHA256 作为产物证据，看到 0 就去看日志。

**Q12：实时备份和定时备份冲突吗？**
不冲突，互补。定时备份提供基础恢复点（全量/增量），实时提供秒级 RPO 和任意时间点恢复。

**Q13：能不能限制某同事只能看不能操作？**
可以，用户管理里按角色 + 附加权限控制，菜单和按钮都受权限约束。

**Q14：邮件通知收不到？**
系统设置配 SMTP（QQ/163/Gmail 要用**授权码**），配完点「发送测试邮件」；再检查智能告警里的「自动通知级别」。

**Q15：加密没生效？**
需要在系统设置配加密密钥（或服务端环境变量 `BACKUP_POOL_KEY`），否则**自动跳过加密**（不报错但也没加密）。

**Q16：AI 相关的功能怎么用？**
AI 智能助手为**收费功能**（需授权启用）；"智能告警"里的预测引擎是本地轻量统计，不依赖外部服务。

**Q17：国产库支持吗？**
支持 kingbase（金仓）、DM（达梦）等，与其它类型同页面配置，命令细节由平台内部适配。

**Q18：迁移和同步到底选哪个？**
一次性搬迁用**数据迁移**；不停机增量、长期同步用**数据同步**。

**Q19：国产化替换场景下，源是 MySQL 目标是达梦/金仓，可行吗？**
可行方向已在平台支持范围内（都已注册到类型体系），实际请按剧本 4/5 先小样本验证，用数据对比确认类型与内容一致。

**Q20：磁盘实在不够怎么办？**
顺序建议：定期清理 → 缩短保留天数 → 配置 L1→L2 冷下沉 → 扩容/L2 目标。

# 附录

## A. 术语表

| 术语 | 含义 |
|---|---|
| 逻辑备份 | 用数据库自带导出命令导出数据（mysqldump/pg_dump/expdp/dexp/sqlcmd…），通用、可挑表 |
| 物理备份 | 复制数据库物理文件（RMAN/xtrabackup/sys_basebackup…），快但恢复需同环境 |
| 全量 / 增量 / 组合 | 全部数据 / 只备份变化部分 / 两者按星期组合 |
| RPO | 允许丢失的数据时间窗口 |
| RTO | 故障到业务恢复所需时间 |
| PITR | 任意时间点恢复（Point-In-Time Recovery） |
| CDC | 变更数据捕获，实时备份/同步的基础 |
| 克隆 / VDB | 从备份快速拉起隔离的可用库副本 |
| 三重备份 L1/L2/L3 | MinIO 热 → S3 冷 → 本地/源端；多级存放 |
| 冷热分级 | 数据从热层按年龄/容量阈值下沉到冷层 |
| 恢复校验 | 定期把备份真实还原一次，证明"能恢复" |
| 数据对比 | 表清单→行数→校验和→抽样，证明"恢复的数据是对的" |
| 黄金回退点 | 迁移/变更前的一次全量备份，作为回滚锚点 |
| 保护等级 | 核心/重要/一般，对应不同 RPO/RTO SLA |
| 幽灵记录 | 记录还在、产物文件已不在磁盘；清理时只标记不虚报释放 |
| 零安装 / 无 Agent | 被保护对象上不安装任何软件、不部署常驻进程 |

## B. cron 速查

| 表达式 | 含义 |
|---|---|
| `0 1 * * *` | 每天 01:00 |
| `0 1 * * 0` | 每周日 01:00 |
| `0 1 * * 1-6` | 周一至周六 01:00 |
| `0 1 1 * *` | 每月 1 号 01:00 |
| `*/15 * * * *` | 每 15 分钟 |
| `0 9,21 * * 1-5` | 工作日 09:00、21:00 |
| `10 3 * * *` | 每天 03:10（定期清理默认值） |
