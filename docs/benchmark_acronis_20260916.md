## 2. Acronis 是什么

### 2.1 产品线

| 产品 | 对象 | 定位 |
|---|---|---|
| **Acronis Cyber Protect Cloud** | 服务提供商（MSP/VAR/主机托管/电信） | 备份 + 灾难恢复 + 网络安全 + 终端管理一体化 |
| **Acronis Cyber Protect** | 中小企业 / 大型企业 | 原生集成安全与终端管理的备份及快速恢复 |
| **Acronis Cyber Protect Local** | 本地部署 / 物理隔离 IT 与 OT | 本地管理服务器，纯本地或混合云存储，适用无互联网或低带宽环境 |
| **Acronis True Image** | 家庭用户 | 备份 + 反恶意软件 |
| **Acronis Snap Deploy** | 企业 | 批量部署 |

**规模**：21,000+ 服务提供商、750,000+ 企业客户、150+ 国家、50+ 数据中心、26 语言。

### 2.2 平台战略：AI 原生 + 统一数据模型

官网首页的核心主张：

> **一个通用数据模型**——每项服务均向同一数据模型写入数据，因此 AI 代理能够跨备份、安全和运维获取完整上下文执行操作，而非逐项孤岛式处理。

服务矩阵：托管式 AI / HCI 与 IaaS / 备份 / 灾难恢复 / 检测与响应 / SaaS 安全 / RMM / PSA。

### 2.3 AI 自主化三级（我认为这是全站最值得学的设计）

| 级别 | 模式 | 威胁检测 | 事件响应 | 补丁部署 | **恢复** |
|---|---|---|---|---|---|
| 1 级 | 辅助 | 异常+行为分析，**给出建议** | 建议：隔离、遏制、建单 | 系统起草部署计划 | **建议还原点** |
| 2 级 | 监督 | 标记与评分 | 系统执行，**须人工先审批** | 批准后发布，**须人工先审批** | **批准后执行恢复，须人工审批** |
| 3 级 | 自主 | 代理自主执行，持续运行 | 按预设策略自动放行或拦截 | 常规补丁自主执行 | **经演练的自动故障切换** |

两个关键点：
1. **每一级都明确"谁批准"**，且 1 级"已内置，需手动开启"——AI 不是默认全权；
2. 3 级恢复的前置条件是"**经演练**"（drilled）——演练通过才允许自动故障切换。

### 2.4 三层网络韧性（Cyber Resilience）

| 层 | 内容 |
|---|---|
| **主动层** | 预防与加固：在攻击造成损害之前预防（漏洞评估、补丁管理、从备份中移除恶意软件） |
| **活跃层** | 实时保护与持续监控：AI/ML 实时防御，检测并消除威胁 |
| **响应层** | 快速响应与恢复：数据快速恢复、集成 DR、一键恢复（含裸机恢复） |

### 2.5 五大能力域（Cyber Protect 产品页原文功能列表）

| 域 | 功能 |
|---|---|
| **备份** | 全镜像和文件级备份 / **不可变备份** / 快速恢复 / 故障安全修补 / 持续数据保护 |
| **安全** | 防恶意软件和防病毒 / 高级威胁监控 / 漏洞利用防范 / 漏洞评估 / 保护协作工具 |
| **灾难恢复** | **即时故障恢复至 VM** / 跨工作负载的自动恢复 / 故障转移到安全恢复点 / **通过运行手册实现更快的 RTO** |
| **终端管理** | 漏洞评估 / 补丁管理 / 软硬件清单 / Cyber Scripting / 基于 ML 的性能监控 / 远程桌面 |
| **邮件归档** | M365 邮件归档 / **不可变存储** / Web 控制台 / 审计日志 |

**关键细节（FAQ 原文）**：
- 备份验证手段：校验和验证 + **AI 辅助的启动后截图或心跳检查** + 脱机数据处理 + 多目标备份；
- **备份恶意软件扫描**：在云中存储备份时检查威胁，确保恢复点是"干净且可安全恢复的"，**降低恢复时再次感染的风险**；
- 灾难恢复：故障转移到云副本前，**云副本会经过漏洞和恶意软件扫描**；
- 代理模块化：仅安装所选保护计划的组件，可**纯备份模式**部署；
- 存储选项：Acronis Cloud / 本地与 NAS / 公有云及 S3 兼容；
- 支持平台：VMware / Hyper-V / Nutanix / Azure VM / **Proxmox** / Citrix / Linux KVM / RHEV / Oracle LVM / Virtuozzo；SaaS：M365、Google Workspace；OS：Windows、macOS、Linux、Android、iOS。

## 4. 蒸馏学习：8 个可学习点

### L1. 不可变备份（Immutable Backup）——**最高优先级，纯空白**

| | |
|---|---|
| Acronis | 明确列为备份核心功能；邮件归档亦强调不可变存储 |
| AIDBM | **无**。有 AES-256-GCM 加密（防**读**），但**无防删/防改** |
| 差距 | 大。加密 ≠ 不可变：拿到凭据的人仍可删除或覆盖备份 |
| 怎么学 | 见 §5 P0 |

### L2. 恢复点"干净"验证——恢复前扫描，防二次感染

| | |
|---|---|
| Acronis | 备份在云端存储时做恶意软件扫描；故障转移前云副本再扫；恢复后用 AI 辅助启动截图/心跳验证 |
| AIDBM | 有深度校验（impdp SQLFILE / RMAN VALIDATE），验证"能不能恢复"，**不验证"恢复出来是否安全"** |
| 怎么学 | 离线环境无法接入病毒库，**只能做启发式异常检测**（见 §5 P1），且必须诚实标注能力边界 |

### L3. AI 自主化三级与审批闸门

| | |
|---|---|
| Acronis | 辅助/监督/自主三级，明确每级"谁批准"；3 级恢复的前置是"经演练" |
| AIDBM | 有 `ai_agent` 会话助手、`ai_alert` 风险预测与修复建议，**但无分级自治，也无审批闸门** |
| 怎么学 | 见 §5 P2。特别是"**演练通过才允许自动故障切换**"——我们已有 `drill` 与 `disaster_link`，天然可落地 |

### L4. 三层网络韧性作为产品叙事框架

| | |
|---|---|
| Acronis | 主动（加固）/ 活跃（监控）/ 响应（恢复）三层，把零散功能组织成一条可讲的故事 |
| AIDBM | 能力其实**都齐了**：主动层=巡检+风险预测+preflight；活跃层=实时备份/CDC+AI 告警；响应层=恢复+演练+克隆+容灾链路 |
| 差距 | 不是功能差距，是**表达与组织差距** |
| 怎么学 | 首页与产品文档按三层重组。这是 S1（可复制交付）的表达层，成本极低 |

### L5. 恢复运行手册（Runbook）实现更快 RTO

| | |
|---|---|
| Acronis | "通过运行手册实现更快的 RTO" |
| AIDBM | `disaster_link` 仅做链路真实检查，**无恢复编排**；恢复是单任务动作，无"按顺序恢复多个库并逐步验证"的编排 |
| 怎么学 | 见 §5 P3 |

### L6. 统一数据模型（AI 原生的地基）

| | |
|---|---|
| Acronis | "每项服务向同一数据模型写入，AI 才能跨备份/安全/运维获取完整上下文" |
| AIDBM | 53 张表，备份/恢复/同步/迁移/克隆各自记录模型 |

### L7. 授权与版本分层

| | |
|---|---|
| Acronis | 按工作负载（工作站/服务器/虚拟主机/M365 席位）许可；标准版 / 高级版 / 高级备份版；含 50–250GB 免费云存储 |

## 5. 吸收方案

### P0：不可变备份与保留锁定（对应 L1）

**目标**：让已生成的备份在保留期内**不可被删除、不可被篡改**，即使凭据泄露或管理员误操作。

四个子能力，按实现难度递增：

| # | 能力 | 实现方式 | 难度 |
|---|---|---|---|
| P0.1 | **保留锁定** | 应用层：删除/覆盖操作前校验 `retention_until`，锁定期内拒绝（含管理员），并记录审计 | 低 |
| P0.2 | **完整性基线 + 周期复检** | 落库 SHA256 基线，周期任务重算比对，漂移即告警（现有 `verify_record` 只在备份后跑一次） | 低 |
| P0.3 | **产物写保护** | Linux 本地存储 `chattr +i`（需权限，失败应明确降级并告警）；对象存储侧启用 S3 Object Lock（若后端支持） | 中 |
| P0.4 | **隔离副本（air-gap）** | 现有磁带 D2T + 摆渡 `ferry_inbox` 已具备物理隔离能力，**包装为"隔离副本"产品能力**并给出推荐拓扑 | 低 |

> 诚实标注：P0.3 在部分文件系统/后端上可能不支持，必须显式声明"本环境未启用写保护"，**不静默降级**（沿用我们的设计原则 6）。

**产出**：`core/immutability.py` + `backup_records` 增列 `retention_until` / `locked` / `checksum_verified_at` + 周期复检任务 + 界面锁标识。

### P1：恢复点安全检测（对应 L2）

离线环境**无法**做真正的病毒查杀（无病毒库、无联网更新）。可行且诚实的是**启发式异常检测**：

| 检测项 | 手段 | 依据 |
|---|---|---|
| 熵值异常 | 计算产物字节熵，异常升高提示已加密 | 加密数据熵接近 8.0 |
| 魔数/格式突变 | 比对文件头魔数与声明类型 | 已有 `ai_alert` 的 gzip/tar/SQL 标记探测可复用 |
| 体积骤变 | 与历史基线比较，骤降提示被清空/截断 | 已有历史记录可算基线 |
| 扩展名异常 | 大规模扩展名变更（如 `.encrypted`） | 勒索典型特征 |

**必须诚实标注为"启发式异常检测，非病毒查杀，不能替代杀毒软件"**。宁可少承诺，不夸大——这符合我们"真实优先"的最高原则。

**产出**：`core/backup_anomaly.py`，结果并入首页健康分与 AI 告警。

### P2：AI 分级自治与审批闸门（对应 L3）

| 级别 | 行为 | 适用 |
|---|---|---|
| 1 级 辅助 | 只给建议，默认不开启 | 风险预测、修复建议、还原点推荐 |
| 2 级 监督 | 系统生成动作，**须人工审批后执行** | 自动恢复、克隆创建 |
| 3 级 自主 | 自动执行 | **仅限"已通过演练"的目标**：自动故障切换 |

**关键约束（直接抄 Acronis 最聪明的一点）**：3 级自动故障切换的准入条件 = 该容灾链路**近 N 天内有成功的演练记录**（`drills` + `disaster_links` 已具备数据基础）。无演练记录 → 强制降级为 2 级人工审批。

**产出**：`core/ai_governance.py`（级别定义、审批流、准入校验）+ 表 `ai_action_approvals`。

### P3：恢复运行手册 Runbook（对应 L5）

**目标**：把"多库按依赖顺序恢复 + 每步验证"编排为可执行、可复用、可留痕的对象。

```
Runbook（定义）
  ├─ 步骤序列：恢复 A 库 → 校验 → 恢复 B 库 → 校验 → 切换连接串 → 业务验证
  ├─ 每步：动作类型（restore/verify/script/approve）、目标、超时、失败策略（中止/继续/回滚）
  └─ 执行实例：逐步状态、耗时、产物、可中断可续跑（复用 P0 的 run/attempt 模型）
```

与现有能力衔接：`cross_host`（跨主机恢复）、`restore_verify`（深度校验）、`clone_service`（VDB）、`drill`（演练）均可作为步骤类型。

**产出**：`core/runbook.py` + 表 `runbooks` / `runbook_runs` / `runbook_step_runs`。

### P4：产品叙事按三层韧性重组（对应 L4）

成本最低、见效最快。首页与文档改为：

| 层 | 聚合的能力 |
|---|---|
| **主动** | 巡检、风险预测、备份前 preflight、不可变与隔离副本（P0）、容量预测 |
| **活跃** | 实时备份/CDC、AI 告警、异常检测（P1）、全链路留痕 |
| **响应** | 恢复与 PITR、VDB 克隆、演练、Runbook（P3）、容灾链路 |

### P5：授权与版本分层（对应 L7，并入 G10）

按**受保护工作负载数**（数据库实例数）+ 版本分层（基础/专业/旗舰）。待商业化决策后启动。

## 7. 明确不跟随的部分（及理由）

| 项 | 理由 |
|---|---|
| **反恶意软件 / EDR / 防病毒** | 需病毒库与联网更新，与"完全离线"根本冲突；且需在受保护端装 agent，与"客户端零安装"冲突。用 P1 启发式检测部分替代，并明确标注能力边界 |
| **终端管理**（补丁管理、远程桌面、软硬件清单） | 属 IT 运维域，偏离灾备定位 |
| **邮件归档 / M365 / Google Workspace 保护** | SaaS 数据保护，我方保护自建数据库，场景不同。客户有需求应单独立项 |
| **整机镜像 / 裸机恢复（BMR）** | 需可启动介质与块级驱动，工程量大；数据库灾备通常先装系统再恢复库，ROI 低 |
| **MSP 多租户** | 未决策（G9）。若做，参考 yak-ops Project Space 的 5 型归属与三态迁移 |
| **AI 第 3 级"自主执行"全面铺开** | 灾备操作破坏性极强，仅对"已演练"的目标开放 3 级，其余保守在 2 级 |
| **按容量计费** | 灾备客户对工作负载数更敏感，采用按实例计数（P5） |

---

## 8. 关于"达到他的功能"的诚实判断

Acronis 是 20+ 年积累的商业产品，覆盖 30+ 工作负载、含 EDR 与 MSP 生态。**全面对等既不现实也不必要**——双方定位不同：

- 它保护**机器与终端**（镜像、系统状态、M365、EDR）；
- 我们保护**数据库**（12 种引擎、表级恢复、PITR、国产库、SQL Server .trn、Oracle RMAN）。

**应当对齐甚至超越的，是重叠区**：不可变与防篡改、恢复点可信、恢复编排与 RTO、AI 分级治理、统一数据模型——这五项我们**现在落后，但都能补**。

**不必追赶的，是非重叠区**：EDR、终端管理、SaaS 归档、裸机恢复。

**应当反过来强化的，是我方独有的**：原生离线/隔离网、客户端零安装、国产数据库覆盖、数据库级细粒度恢复、不仿真如实失败。这五条 Acronis 做不到——其中"离线"它还要专门出一个 Local 版来补。

## 9. 落地路线

| 阶段 | 内容 | 依赖 | 风险 | 价值 |
|---|---|---|---|---|
| **第一步** | P4 叙事重组 + P0.1/P0.2/P0.4（保留锁定、周期复检、隔离副本包装） | 无 | 低 | 高（P0.1/0.2 成本极小） |
| **第二步** | P0.3 产物写保护 | P0.1 | 中（依赖存储后端能力） | 高 |
| **第三步** | P1 启发式异常检测 | 无 | 低 | 中 |
| **第四步** | P2 AI 分级治理 + 审批闸门 | 无 | 中 | 高 |
| **第五步** | P3 Runbook 编排 | 统一作业模型（yak-ops P0） | 中高 | 高 |

**建议第一步立即启动**：P0.1（保留锁定）与 P0.2（周期复检）都是**极小改动、极大价值**——在 `backup_records` 加两个字段 + 一个删除前置校验 + 一个周期任务，就把"备份可被删"这个当代灾备最大的结构性风险补上。

## 10. 一句话结论

Acronis 最值得学的不是它的功能清单，而是三件事：**把"不可变"当作备份的一等属性**、**把 AI 的自治边界用级别和审批明确下来（且以演练作为自动化的前置门槛）**、**把恢复从单个动作提升为可编排的运行手册**。这三件事都不依赖它的技术栈，也都不违背我们的离线与零安装约束——而"不可变"这一项，是我们目前**完全空白**且必须尽快补上的。
