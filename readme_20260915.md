# AIDBM 平台更新说明（2026-09-15）

本次更新涵盖：**全面压力测试套件与高并发加固、大库备份性能提速（50~110 倍）、断点续传（逻辑备份流 + 物理备份等固定产物全覆盖）、任务级超时 / 重试 / 限速配置**。

版本：`v1.4.6` + `v1.4.7`；镜像：`ghcr.io/zhh9126/backup-platform:v1.4.7`。

> 起因是一条真实的现场反馈：**10GB 级库在同机备份，网卡流量只有 600KB/s，跑到 1.4GB 后被超时砍掉，重试又从 0 开始，永远跑不完。**
> 本次围绕"大库能不能备份得完"与"平台扛不扛得住批量任务"两条主线做完完整闭环：先用压测暴露并发缺陷，再定位并修复传输层根因，最后补上断点续传让中断不再重跑。

## 一、全面压力测试套件 + 高并发加固（v1.4.6）

### 1.1 新增压测工具 `scripts/stress_test_full.py`

6 阶段全链路压测（Python + requests + 线程池），结果可落盘 JSON：

| 阶段 | 内容 |
| --- | --- |
| A | 批量创建 N 个备份任务（1000+） |
| B | 批量触发「立即备份」，统计 success / failed |
| B2 | 落库对账：直连元库核对每条触发都有记录，success 记录 size>0、有 sha256、产物文件真实存在 |
| C | 全接口压测：自动从 `app.url_map` 发现全部 GET 接口（动态参数用真实 id 填充）并发请求 |
| D | 数据返回校验：18 项断言（结构 / CRUD 往返 / 关联一致性 / 分页筛选 / 异常入参返回 4xx 而非 5xx / 并发读一致） |
| E | 混合读写：持续 N 秒读压测 + 20% 写操作混杂 |
| F | 写接口并发：创建-删除配对压测，并混入非法负载验证不会 500 |

```bash
python scripts/stress_test_full.py                                  # 全量 1000 任务
python scripts/stress_test_full.py --tasks 1200 --concurrency 150    # 更大并发
python scripts/stress_test_full.py --tasks 60 --api-req 2            # 快速冒烟
python scripts/stress_test_full.py --skip-backup                     # 只压接口
python scripts/stress_test_full.py --report /tmp/stress.json         # 结果落盘
```

> 注：Dockerfile 不 `COPY scripts/`，压测脚本不入生产镜像（与既往设计一致）。

### 1.3 压测暴露并修复的缺陷

| # | 问题 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | 内置 Web 服务未开启多线程（`app.run` 缺 `threaded`） | 批量提交 / 触发排队，高并发直接超时 | `run.py` 增加 `threaded=config.WEB_THREADED`（默认开，可用环境变量关闭） |
| 2 | SQLite 连接未设置 busy 超时 | 多线程并发写元库抛 `database is locked` | `core/db.py get_conn()`：`timeout=30` + `PRAGMA busy_timeout=30000` + `synchronous=NORMAL` |
| 3 | **调度器 reload 并发竞态**：遍历 job 快照后逐个 `remove_job()`，并发 reload 时抛 `JobLookupError` | 并发建 / 删任务必现 **HTTP 500**（压测 60 并发即 11 次） | `core/scheduler.py`：序号 + 执行锁做**请求合并**（并发 N 次 reload 只真正重建 1~2 次）+ `remove_job` 容错 |
| 4 | `/api/tasks/{id}/list-tables` 目标库连不上返回 **500** | 配置 / 环境问题被当成服务端异常，污染监控 | 改为 **400 + error 文案** |
| 5 | `/api/records` 不支持 `limit`，固定返回 500 条 | 无法分页，大数据量下拉取过重 | 支持 `limit`（上限 500 保护） |

修复前后（同一规模 60 任务 / 30 并发）的 5xx 计数：A 阶段 11 → **0**、C 阶段 2 → **0**、E 阶段 16 → **0**。

### 1.4 性能结论与调优建议

- **备份执行吞吐约 13~15 个/秒**（轻量脚本）。瓶颈在单次备份的固定开销（元库写锁、日志、产物落盘与 sha256），**不在并发度**：`max_concurrent_backups` 从 2 调到 16，300 任务 QPS 仍为 14.5，无提升 → 不建议盲目放大并发，应按目标数据库承载能力设置。
- **生产建议 gunicorn**：内置 werkzeug 在高并发下线程数无上限（压测峰值 172 线程），推荐 `gunicorn -w 4 --threads 8 -b 0.0.0.0:8080 run:app`。
- 压测客户端 `pool_maxsize` 必须 ≥ 并发数，否则会出现客户端侧 "Connection pool is full" 的假瓶颈（脚本已设为 512）。

## 二、大库备份提速：修复 SSH 数据通道的 O(n²) 拷贝（v1.4.7，本次重点）

### 2.1 根因

`core/engines/file.py` 的 SSH 数据通道是**所有远程 dump / tar 流的唯一入口**，叠加了三个性能坑：

| 坑 | 原实现 | 后果 |
| --- | --- | --- |
| **O(n²) 内存拷贝（主因）** | `out += sess.recv(65536)` | `bytes` 不可变，每追加 64KB 都要把**已有全部数据** memcpy 一遍。累积到 1.4GB 时单次追加要复制 1.4GB，有效吞吐掉到几百 KB/s——**数据量越大越慢**，与现场完全一致 |
| 每轮只读 64KB + 无数据固定 `sleep(0.05)` | 主循环 | 等效限速约 1.3MB/s，系统调用开销成倍增加 |
| 全量产物先攒在内存再落盘 | `remote_db_dump()` 返回 bytes | 10GB 库 → 10GB 内存 / 交换，爆内存风险 |
| 附带：写死 `timeout=3600` | 各 dump 调用点 | 大库必然被打断，且重试＝从头重跑（管道没有 offset 语义） |

### 2.2 修复：统一重写为 `_ssh_exec_stream()`

- 支持 `out_file` / `out_path`：**边收边写盘**，内存恒定（256KB 块），不再把 10GB 产物攒在内存；
- 单次 `recv` 从 64KB → **256KB**；**仅在无数据时** sleep 2ms（数据充足时不休眠）；
- SSH 传输窗口 2MB → **16MB**、单包 32KB → **128KB**（高带宽 / 高 RTT 链路不再苦等 window adjust）；
- `timeout=0` 表示不限总时长；新增 `idle_timeout` 只在"长时间无数据"时判失败，区分**大表读得慢**与**真卡死**；
- **限速改由平台侧实现**（`rate_kbps`），不再要求数据库服务器安装 `pv`——符合"被备份服务器零安装"硬约束；
- 每 **30s** 输出传输进度（已传大小 + 速率 MB/s）到操作日志，大库备份不再黑屏干等；
- 新增 `_ssh_exec_pipe_to_file()`（落盘版）；旧 `_ssh_exec_pipe()` 保留兼容，内部改用 `bytearray` 消除 O(n²)。

### 2.3 覆盖面：所有数据库类型与文件备份统一受益

`_ssh_exec_pipe()` 是各引擎远程操作的公共入口，`_ssh_exec_stream()` 在其下层，因此**本次提速对以下场景全部生效，无需逐引擎适配**：

- 逻辑备份：MySQL / MariaDB / PostgreSQL / 金仓 / Oracle（含 Data Pump）/ 达梦 / SQL Server / MongoDB / Redis 等经由 SSH 的远程 dump 流；
- 物理备份：xtrabackup / mariabackup / pg_basebackup / sys_basebackup 等远端压缩 tar 流；
- 文件备份与恢复：远端目录打包拉回、跨主机恢复时的产物推送；
- 自定义脚本备份：远端脚本产物拉回（`custom_artifact_dir`）。

### 2.4 实测对比（平台机 ↔ 数据库机 同机 SSH，`dd` 输出 N MB）

| 数据量 | 旧实现 | 新实现 | 提速 |
| --- | --- | --- | --- |
| 100 MB | 110.5 s（0.9 MB/s） | 2.0 s（50.5 MB/s） | **55×** |
| 150 MB | 249.1 s（0.6 MB/s） | 2.2 s（68.6 MB/s） | **113×** |
| 300 MB | 17 min 仍未传完 | 秒级 | — |

> 旧实现速率随数据量单调下降（0.9 → 0.6 MB/s），正是 O(n²) 的典型特征；
> **现场实测到的 600KB/s 与 150MB 档完全吻合**，可确认同一根因。

## 三、断点续传：中断后不重跑 dump（v1.4.7）

光提速不够——几十 GB 的库在受限链路上一次要数小时，期间网络抖动、平台重启都可能发生。**管道没有 offset 语义**，一旦中断只能从头再来。因此改为两段式：

```
① 远端后台导出    mysqldump → 远端暂存文件（setsid nohup，SSH 断开也继续）
② 平台增量拉取    按 offset 继续读，边导出边传；中断后从已传字节续，不重跑导出
```

- 断点元数据：`<产物目录>/.resume_t<任务id>_<库类型>.part{,.meta}`，默认保留 12h（`BACKUP_RESUME_TTL`）；
- 续用条件严格校验：同一主机 + 压缩 / 格式参数一致 + 未过期，否则自动清掉旧残留重新导出；
- 成功后**自动清理**远端暂存（`BACKUP_REMOTE_STAGE`，默认 `/tmp/bk_stage`）与本地 `.part` 半成品；
- 导出命令**原本就在数据库服务器上执行**（`mysqldump` 随 DBMS 自带），平台侧不向目标机安装任何工具；
- 关闭方式：任务高级选项取消勾选「断点续传」（回退到旧的 stdout 直传通道）。

### 验证（MySQL 5.7，52 万行 / 270MB 库）

1. 限速 100KB/s 启动备份，传到 **208,896 字节** 时 `kill -9` 平台进程；
2. 重新执行 → 日志输出 `命中断点续传`，`resumed=True`，**1.4s 完成**（未重跑 mysqldump）；
3. 产物 1,057,025 字节，解压后 **270,994,317 字节**，含完整 52 万行数据与 `-- Dump completed on ...` 结尾标记；
4. 完成后本地 `.part/.meta` 与远端暂存均已自动清理。

引擎层端到端：`MySQLEngine.backup(FULL)` → `success=True`，产物 `.../mysql/8888_e2e_bigdb/20260915_120008__e2e_bigdb__full.sql.zst`，message：`通过 SSH 在数据库服务器(root@127.0.0.1:22)执行 mysqldump 成功 | 1.0 MB`。

### 3.4 固定产物形态：物理备份 / Data Pump / .bak / 脚本产物（同一模式接入）

逻辑备份是**流式**产物且自带 rc 标记文件；但**固定产物**（先把数据写成一个或多个文件，再一次性拉回）有两个差异，本版已按同一模式打通：

| 差异 | 逻辑备份（§3 原通道） | 固定产物（本版新增） | 应对 |
| --- | --- | --- | --- |
| 远端是否有完成标记 | 有（dump 脚本写 rc 文件） | **没有** | 改用**「远端文件连续 N 秒不再增长」**判定写盘结束（`stable_secs`，固定产物默认 3s：备份命令返回后文件不再变化，短窗口即可确认） |
| 产物重跑代价 | 中等（重新 dump） | **极高**（xtrabackup / pg_basebackup / RMAN 可能跑数小时） | 远端路径**确定性化**（按任务固定，不含随机时间戳）+ `.bkdone` 完成标记 → 拉回中断后重试**跳过备份执行**，直接从断点续传 |

统一入口（`core/remote_dump.py`）：`sftp_pull_resumable()`（单文件）/ `_pull_remote_tars()`（PG 系多 tar）/ `remote_artifact_ready()` / `mark_remote_artifact_done()` / `cleanup_remote_artifacts()`。本地断点文件按 **任务 + 产物 key** 区分（`.resume_t<任务id>_<类型>[_key].part`），同一个任务的多个备份片 / 多个 tar 不会互相覆盖。

| 场景 | 远端产物（确定性路径） | 复用标记 | 备注 |
| --- | --- | --- | --- |
| MySQL / MariaDB 物理（xtrabackup / mariabackup） | `/tmp/bk_stage/fixed/t{id}_{dbtype}_phys_{full,inc}.tar.gz` | 同名 `.bkdone` | 全量 / 增量各自独立；推送的临时二进制照旧清理 |
| PG 系物理（pg_basebackup / sys_basebackup） | `/tmp/bk_stage/fixed/t{id}_{tool}_phys.d/`（目录形态） | 目录内 `.bkdone` | 逐个 tar（`base` + WAL）续传拉回 |
| Oracle RMAN | `/u01/app/oracle/backup/ora_bkp_t{id}_*.bkp` | `.bkdone_t{id}` | 逐备份片续传，非复用路径先清同名旧片 |
| Oracle Data Pump（expdp） | `DATA_PUMP_DIR/bk_t{id}.dmp` + `.log` | `.bkdone_t{id}` | 导出前删除同名 dmp，避免 expdp 报"文件已存在" |
| SQL Server（FULL / DIFF / LOG） | `{备份目录}/{库}_{类型}_t{id}.{bak,diff,trn}` | `{产物}.bkdone` | Windows 走正斜杠 SFTP 路径；T-SQL 本就带 `WITH INIT` |
| 达梦物理（联机 / dmrman） | `/home/dmdba/dm_bkp_t{id}.tar.gz` | 同名 `.bkdone` | 复用时跳过 disql/dmrman 与打包 |
| 自定义脚本产物 | `$PLATFORM_BACKUP_DIR/*` | 不复用（脚本语义由用户定义） | 按文件名做 key 逐个续传 |

> **零残留约束不变**：完成标记只在**尚未成功拉回**时保留；产物一旦完整落盘，远端产物 + 标记 + 推送过的临时二进制全部清理，
> 数据库服务器上不留任何平台产物或工具。

**验证**（模拟远端 SFTP 的一次性全场景校验，22 条断言全过）：

```
① 边写边拉（6MB 文件慢速增长）→ 拉回 6,291,456 字节，sha256 与远端一致，未触发误判提前结束
② 传输到 1,048,576 字节时注入断链 → 本地保留 .part 半成品 1,048,576 字节，未生成最终产物
③ 重试 → hit 续传标记，首个读偏移 = 1,048,576（未重传），完成 8,388,608 字节，sha256 一致，拉取后 .part/.meta 自动清理
④ 多产物按 key 隔离：base.tar.gz / pg_wal.tar.gz 各自断点、各自续传
⑤ 复用判定：无标记 → 不可复用；写入 .bkdone → 可复用；产物小于阈值 → 不可复用
⑥ 成功拉回后 cleanup_remote_artifacts → 产物与标记均消失（远端零残留）
⑦ 目录形态（PG）：探测 size=4096 → 写目录内 .bkdone → reusable=True
```

> 说明：以上为 **SFTP 通道层**的一致性验证（以本地目录模拟远端 SFTP，驱动的是线上真实的续传代码路径，
> 包括 `_sftp_pull_incremental` 的稳定判定分支与断点元数据读写）；
> 各数据库引擎的**备份执行本体**未做改动，仍沿用此前的真机实测结论。
> 本次未连接 129/133/137/158 等真机环境，如需复测物理/逻辑备份的真实拉回，按 §3 的验证步骤在原环境重跑即可。

## 四、任务级传输参数（新增 5 个高级选项）

旧实现把超时写死 3600s、重试间隔写死 5s 指数退避，大库无法针对性调整。现全部开放到「任务 → 高级选项」（存 `extra_options`，全局默认可用环境变量覆盖）：

| 界面字段 | extra_options 键 | 默认 | 环境变量（全局默认） | 说明 |
| --- | --- | --- | --- | --- |
| 执行超时 | `cmd_timeout` | **0（不限）** | `BACKUP_CMD_TIMEOUT` | 单次执行总时长上限；0 = 不限，靠空闲超时兜底，**不再让大库被写死的时间砍掉** |
| 空闲超时 | `idle_timeout` | 1800 s | `BACKUP_IDLE_TIMEOUT` | 连续这么久没有任何数据流出才判失败，区分"大表读得慢"与"真卡死" |
| 失败重试间隔 | `retry_interval` | 60 s | `BACKUP_RETRY_INTERVAL` | 旧版 5s 指数退避；大库失败后立刻重试没意义，默认给链路留出恢复时间 |
| 失败重试次数 | `retry_max` | 3 | `BACKUP_RETRY_MAX` | 0 = 不重试；仅网络 / 超时类错误重试 |
| 断点续传 | `resume_enabled` | 开 | `BACKUP_RESUME_ENABLED` | 中断后从已传字节继续 |
| （流量控制 KB/s） | `bandwidth_limit` | 0 | — | 平台侧限速，**不依赖远端 `pv`** |
| — | — | 12 h | `BACKUP_RESUME_TTL` | 断点元数据保留时长 |
| — | — | `/tmp/bk_stage` | `BACKUP_REMOTE_STAGE` | 远端暂存目录（需能容纳压缩后产物） |
| — | `stable_secs` | 20 s（固定产物拉回时用 3 s） | `BACKUP_STABLE_SECS` | **固定产物专用**：远端文件连续这么久不再增长即判定写盘结束（无 rc 标记，见 §3.4） |
| — | `keep_remote_done` | true | `BACKUP_REMOTE_KEEP_DONE` | 拉回中断期间是否在远端保留产物 + 完成标记，供重试复用；成功拉回后仍清理 |

## 五、本次一并修复的缺陷

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| `remote_has_tool()` 另起 SSH 连接失败时被当成"没装 zstd" | 大库备份白白丢掉压缩（产物体积数倍放大） | 改用**当前已建立的连接** `command -v zstd` 探测，失败才回退另起连接 |
| SFTP 不会递归创建父目录 | 远端暂存目录不存在时写脚本直接 ENOENT | 启动导出前先 `sftp.mkdir(stage)` |
| `2>` 写在管道末尾只捕获了压缩程序的 stderr | 导出失败时 `.err` 为空，查不到真实原因 | 脚本改为 `exec 2> err`，整条管道（含 mysqldump 自身）的 stderr 都落文件 |
| 本机自测场景 `sftp.put(path, path)` 自我截断 | 配置文件被清空导致 dump 鉴权失败 | 源 / 目的路径分离 |

## 六、生产建议

- **10GB 以上库：执行超时保持 0（不限）**，靠「空闲超时 1800s」兜底；**务必开启断点续传**——这是大库能否跑完的分水岭。
- 远端 `/tmp` 空间不足时用 `BACKUP_REMOTE_STAGE` 指定其他暂存目录。
- 需要限速时在任务「流量控制」填 KB/s（平台侧实现，数据库服务器不用装任何东西）。
- 大量任务并发的生产环境按上文部署 gunicorn，元库建议迁移到 MySQL / PostgreSQL（SQLite 已加 busy 超时，但写仍是串行锁）。

## 九、已知边界与后续

- **通用提速层**已覆盖全部数据库类型与文件备份（见 2.3），无需逐引擎适配；
- **完整 SFTP 断点续传已覆盖全部产物形态**：逻辑备份流（rc 标记判定）+ **固定产物**（物理备份 tar / Oracle Data Pump `.dmp` / SQL Server `.bak` / 达梦备份集 / 自定义脚本产物，按「文件连续 N 秒不再增长」判定），详见 **§3.4**——上一版"固定产物待接入"的边界已闭合；
- **远端产物复用**：固定产物改为**确定性远端路径 + `.bkdone` 完成标记**，拉回中断后重试会**跳过备份执行**（xtrabackup / pg_basebackup / RMAN 可能跑数小时）直接从断点续传；成功拉回后仍按原规则清理，**数据库服务器零残留**；
- 仍存在的边界：① 断点有效期 12h（`BACKUP_RESUME_TTL`）之外的中断仍需重跑备份；② 备份**执行过程中**被强杀（未写完成标记）时，产物不可用只能重跑；③ 「文件连续 N 秒不再增长」是启发式判定，极低概率下可能把"恰好 N 秒无写入"误判为写盘结束——固定产物是在备份命令返回后才拉回，实际不发生。

> 压测报告与逐接口延迟数据见 [docs/stress_test_report_20260915.md](docs/stress_test_report_20260915.md)、[docs/stress_report_20260915.json](docs/stress_report_20260915.json)。

## 十、数据价值挖掘模块升级：从「脱敏导出」到「资产治理闭环」

原模块只有一个 DEMO 仿真数据的脱敏导出工具。参考业界数据资产管理平台的通行路径（**盘点 → 分级 → 评估 → 治理 → 运营**），
将其重构成五个看板，并把每一环都落到**平台真实的元数据与备份产物**上：

| 看板 | 回答的问题 | 数据来源 |
| --- | --- | --- |
| 资产盘点 | 我有哪些数据资产？多大？分布在哪？ | `backup_tasks` / `backup_records` / `backup_sets` 聚合 |
| 敏感发现与分级 | 里面有没有敏感数据？什么级别？ | **真实读取备份产物内容**（支持 .gz/.bz2/.xz/.zst 透明解压） |
| 价值评估与治理 | 值多少钱？哪些该归档/清理/补保护？ | 六维打分 + 冷热分层 + 量化收益的 actionable 建议 |
| 合规概览 | 能不能拿出来给审计看？ | PIPL / GB/T 35273 / PCI-DSS / 等保 2.0 检查项 |
| 脱敏导出 | 怎么安全地用起来？ | 既有能力 + 扫描结果一键生成规则 |

### 10.1 敏感数据发现与分级（`core/sensitive_scan.py`，新增）

对标业界 Discovery + Classification 能力，特点：

1. **内容级识别**，不是只看列名——能挖出混在自由文本 / JSON / 日志里的敏感值；
2. **校验算法二次确认**（下方标 ✅ 项），把误报压到极低：身份证采用 GB 11643 MOD 11-2 校验位、
   银行卡采用 Luhn(模 10)、统一社会信用代码采用 MOD 31、手机号采用号段表；
3. **四级分级**依据 **GB/T 43697-2024**《数据安全技术 数据分类分级规则》（区分核心/重要/一般数据，
   一般数据按敏感程度细化）：**L4 重要 > L3 敏感 > L2 内部 > L1 公开**；
4. **合规标签**：PIPL / GB/T 35273 / PCI-DSS / GDPR / 等保 2.0，可直接用于举证材料；
5. **原始值零留存**：扫描结果只输出脱敏样例（`138****1234`），既不写库也不写日志，
   避免"为了治理敏感数据而新造一个泄漏面"；
6. **自带建议脱敏动作**，可一键转成脱敏规则喂给「脱敏导出」。

| 类别 | 分级 | 判定方式 |
| --- | --- | --- |
| 居民身份证号码 | L4 | 正则 + 校验位 ✅ |
| 银行卡 / 信用卡号 | L4 | 正则 + Luhn ✅ |
| 口令 / 密钥 / Token（键值型） | L4 | 键值上下文正则 |
| 私钥 / 云 AK（PEM、AKID、bcrypt 串） | L4 | 内容特征正则 |
| 护照 / 港澳通行证 | L4 | 正则（弱判定） |
| IBAN / 含凭证的 URL | L4 | 正则 |
| 手机号码 | L3 | 正则 + 号段表 ✅ |
| 电子邮箱 | L3 | 正则（脱敏保留域名） |
| 统一社会信用代码 | L3 | 正则 + MOD 31 校验 ✅ |
| IP 地址（GB/T 35273 属个人信息） | L3 | 正则 + 合法性校验 ✅ |
| 车牌号、MAC 地址、出生日期 | L2~L3 | 正则 / 泛化建议 |

误报实测：普通业务文本（`订单 SO-20240915-000123 金额 1228217.50`）**零命中**；
16 位以上流水号因 Luhn 校验被正确排除。

### 10.2 资产盘点（`core/asset_inventory.py`，新增）

以「备份任务 = 数据资产」为单位，聚合出 KPI、分布与趋势：**资产数 / 实例数（去重 host:port）/
累计容量 / 周期新增与环比 / 受保护资产占比 / 平均价值分**，以及近 N 天增长趋势、冷热分层分布、
存储层级占用（L1 本地 / L2 MinIO / L3 S3）、数据库类型分布、实例 Top 10。

另含**重复产物识别**：同一 `sha256` 被多次落盘 → 直接算出对象级重删可释放空间。

### 10.3 价值评估与冷数据治理

六维打分模型（总分 100）：**活跃度 25**（近周期批次 / 增量链路 / 实时保护）、**保护完备 20**
（定时 / 启用 / 保留策略 / 成功率 / 校验率）、**规模 15**、**可恢复性 15**（恢复与演练成功率 / 克隆引用）、
**业务辐射 15**（CDC / 同步 / 克隆 / 业务系统归属）、**合规敏感度 10**（来自敏感扫描的国标等级）。

冷热分层：热（≤7 天）/ 温（≤30 天）/ 冷（≤90 天）/ 冰封（>90 天或任务已停用）。

自动产出 6 类 **带量化收益**的治理建议（按危险度与可释放空间排序）：

| 建议 | 触发条件 | 收益指标 |
| --- | --- | --- |
| 降级到 L3 冷存储 | 冷/冰数据仍占本地空间 | 可释放本地容量 |
| 清理无主占用 | 任务已停用但产物仍在 | 可直接回收容量 |
| 补定时保护 | 未配置调度（只能手动触发） | 受影响资产数 |
| 补恢复验证 | 从未做过恢复/演练 | 受影响资产数 |
| 全局重删 | 存在相同 checksum 的重复产物 | 可释放空间 |
| 修复失败率 | 成功率 < 80% | 受影响资产数 |

### 10.4 合规概览

7 项检查（PIPL / GB/T 35273 / PCI-DSS / 等保 2.0）：识别覆盖率、重要数据脱敏外发留痕、
备份留存周期合规、敏感资产恢复演练、敏感资产定时保护、敏感数据异地副本、宽松导出告警。

> **关键设计**：检查项分为「已评估 / 未评估」。当识别覆盖率不足时，依赖敏感清单的检查项一律记为
> **未评估并不计入总分**——否则会出现「没扫描 = 没发现 = 100 分」的虚假安全感。
> 实测：62 个资产、扫描 1 个 → 合规分 **48 / 待整改**，C1 覆盖率 **2%**，其余敏感项显示「未评估」。
