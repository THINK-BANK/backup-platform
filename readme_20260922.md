## 1. 「组合 / 增量任务保存后无法编辑」（用户反馈，缺陷修复）

### 1.1 现象

任务是「组合（全量+增量）」或「增量」类型时，在任务列表点「**编辑**」，页面**毫无反应**：弹窗打不开，控制台也不一定看得到错误。同一批里的「全量」任务是正常的。

### 1.2 根因（三层叠加，第三层导致"静默"）

1. **元素 id 对不上**：页面真实元素是 `t_incremental_days` / `t_incremental_time`，而旧 JS 按前缀拼成了 `t_inc_days` / `t_inc_time`，取值恒为空 → 后续逻辑拿到脏数据。
2. **万能代理对象是"真值"**：`BKP.$` 在元素不存在时返回一个万能代理对象。这个对象参与 `if (el)` 判断恒为 **true**，于是代码继续往下走。
3. **静默吞异常（无法定位的根因）**：拿到代理对象后 `el.querySelectorAll(...).forEach(...)` 得到 `undefined`，调用即抛 `TypeError`；该异常在 `openTaskModal` 的执行链上**没有任何 try/catch**，整个 `openTaskModal` 被打断且不被上层感知 —— 用户侧看到的就是"点了没反应"。

### 1.3 修复（三层各修一处，互为防线）

| 层 | 修改 | 效果 |
|---|---|---|
| 基础工具层 | `static/js/bkp-core.js`：代理对象对 `querySelectorAll` 返回 `[]`、对 `querySelector` 返回 `null` | 从源头杜绝"代理对象流出 A 类 API" |
| 取值层 | `static/js/app.js`：新增 `_mixedIds()` / `_firstRealEl()` / `_checkboxesOf()` / `_daysFromCron()`。**用 `document.getElementById` 逐个取候选 id**（含 `_inc_` → `_incremental_` 兼容），并与 GS 私有原因/按天勾选做严格代数运算；缺失时**从 cron 星期段反推勾选** | id 重命名/历叐数据缺按天配置都能正确回填 |
| 调用层 | `OpenTaskModal` / `openFileTaskModal` / `editTask` / `editFileTask` 全部加 **try/catch + toast** | 以后再出同类问题，**页面会弹出红色提示**而不是静默 |
| 顺带补齐 | `templates/tasks.html` 缺失的 `t_ssh_host`（已纳管 SSH 主机下拉） | 高级选项里"指定纳管主机"此前不生效 |

> 配套：清理是真正的第三层防线——即便前两层出问题，用户也能立刻看到可读提示并提交反馈，而不是"没反应"。

## 2. 新增「备份产物定期清理」

### 2.1 为什么需要

备份会一直积累。手工删文件风险极大（删错、删到保留期内、账实不符），而平台此前**没有**统一的按保留策略回收能力。

### 2.2 实现

**后端 `core/backup_cleanup.py`**

- 按**每个任务自己的** `retention_days` / `retention_count` 扫描；
- **keep_min 兜底**：每任务最后 N 份成功备份无条件保留，**永远不会清空的最后一个可用备份**；
- **`_is_managed_path` 路径护栏**：只允许删备份根目录之内的文件，越界一律拒绝（防误删宿主机目录）；
- **dry_run 预览**：先看清单与预计释放空间，确认后再真删；
- 清理后**默认把记录标记为 `expired_cleanup`（保留审计轨迹）**，可选 `purge` 才物理删行；
- 幽灵记录（记录还在、产物已不在磁盘）只对齐账本，**不虚报释放空间**。

**接口 `api/backup_cleanup.py`**（已注册到 `api/__init__.py`）

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/v1/backup-cleanup/config` | 取清理配置 |
| POST | `/api/v1/backup-cleanup/config` | 保存配置（开关 / cron / 最少保留 / 是否删记录） |
| POST | `/api/v1/backup-cleanup/preview` | 全量扫描预览（不删数据） |
| GET | `/api/v1/backup-cleanup/preview/<id>` | 单任务预览 |
| POST | `/api/v1/backup-cleanup/run` | 立即清理（支持 dry_run） |

**调度 `core/scheduler.py`**

- 新增 `_register_cleanup()`：job id = `backup_cleanup`，cron 取自 `system_config.cleanup_cron`，默认 `10 3 * * *`（每天 03:10）；
- `start` 与 `reload` **两条路径均已注册**（顺带修掉此前 reload 会丢 gfs/ferry job 的缺陷）。

**前端**

- 数据库备份页工具栏新增黄色按钮「**定期清理**」+ 弹窗：开关 / cron / 最少保留 / 是否删记录 / **扫描预览（不删数据）** / 立即清理；
- 预览表列：任务｜类型｜策略｜现有成功备份｜待清理｜可释放；
- `bkp-core.js` 的 `statusBadge` 增加 `expired_cleanup` / `expired_gfs` 两种状态徽章。

### 2.3 验证

- 新增自测 `tests/test_backup_cleanup.py`：**13 passed**（含 UI 契约静态回归，防止 front-end/后端接口再漂移）；
- 本机 15:36 手工跑过一次**真实清理**：24 条记录被标记 `expired_cleanup`，其中 2 条真实删除了磁盘文件；
- 界面默认：清理开关 **enabled=True**、每任务最少保留 **1 份**、cron `10 3 * * *`。

> 注意：任务表单里「保留天数」默认 30 天，但决定清理判据的第二个字段 `retention_count`（保留份数）**当前任务表单未开放输入框**，需要时由管理员通过接口设置；未配置保留天数的任务**不会被清理**（不会被误伤）。
