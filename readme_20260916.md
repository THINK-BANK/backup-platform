## 一、Neo4j 图数据库备份引擎（新增）

### 1.1 背景与设计取向

图数据库此前是平台的能力空白。Neo4j 与关系库最大的差异是：**社区版没有在线备份能力**（`neo4j-admin database backup` 与 `STOP DATABASE` 都是企业版专属），且 `neo4j-admin database dump` **要求数据库离线**——社区版只能停掉整个服务/容器，才能释放 `/data/databases/<db>/database_lock`。

因此本引擎按**三通道**实现，并在不支持时**诚实回退 + 如实说明**，绝不用"假成功"掩盖能力边界：

| 通道 | 命令 | 是否停机 | 产物 | 恢复命令 | 适用版本 |
| --- | --- | --- | --- | --- | --- |
| `dump` | `neo4j-admin database dump --to-path --overwrite-destination=true` | **需离线** | `.dump` | `neo4j-admin database load` | 社区版 / 企业版 |
| `backup` | `neo4j-admin database backup --type=AUTO\|FULL\|DIFF` | **在线** | `.backup.tar.gz`（远端目录打包拉回） | `neo4j-admin database restore` | **仅企业版** |
| `apoc_cypher` / `apoc_json` / `apoc_csv` | `apoc.export.*`（经 cypher-shell） | **在线** | `.cypher` / `.json` / `.csv.zip` | `apoc.cypher.runFile` / `apoc.import.json` / `apoc.import.csv` | 需装 APOC 插件 |

选择方式：任务 → 高级选项 `extra_options.neo4j_method`（`auto|dump|backup|apoc_cypher|apoc_json|apoc_csv`，默认 `auto`）。

### 1.2 关键实现点

1. **离线 dump 的官方做法（Docker 场景）**：`docker stop` → 起一次性**临时容器**挂载同一份 data 目录执行 dump → `docker start`。
   绝不用临时容器去 dump 正在运行的库——两个容器抢同一把 `database_lock`，必然报 `The database is in use`。
   裸机/包安装则执行停服命令（默认 `systemctl stop neo4j`）→ dump → 起服。
2. **企业版在线增量**：增量链目录在远端固定保留（`<stage>/chain_<taskid>`），`--type=AUTO` 自动判定全量/差异；备份前后比对目录列表，**只拉回本次新增/变化的产物**（避免每次全量重传）。
3. **能力诚实声明**：新增 `_ENGINE_META_OVERRIDE`（`core/engines/__init__.py`）按引擎**真实能力**逐项登记，修正了 `engine_meta_map` 默认值偏乐观（全部 True）的问题：

   ```python
   "neo4j": {
       "icon": "bi-diagram-3",
       "backup_modes": ["logical"],          # 无数据文件级物理通道
       "supports_incremental": True,          # 仅企业版在线 backup 通道原生支持 --type=DIFF
       "supports_full_instance": False,
       "supports_sync": False,
   }
   ```

4. **连接探测**：`core/probe.py` 新增 `_probe_neo4j`——`cypher-shell` 优先（bolt，`RETURN 1 AS ok`），缺失时回退官方 HTTP 事务接口 `POST /db/<db>/tx/commit`（Basic 认证、只读、不落数据）；两条路都不可用时返回「未知」而非误报警。
5. **执行位置**与平台其它引擎一致：优先 SSH 到数据库服务器执行，失败回退平台本机（零客户端安装原则）。

### 1.3 新增一种数据库必须登记的全栈点（已全部补齐）

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 引擎 | `core/engines/neo4j.py`（1180 行） | `Neo4jEngine(BackupEngine)`：backup / restore / verify_record |
| 注册 | `core/engines/__init__.py` | `ENGINE_REGISTRY["neo4j"]`、适配层分级 `peripheral_api`、元信息覆盖 |
| 配置 | `config.py` | `SUPPORTED_DB_TYPES`、`DEFAULT_PORTS["neo4j"]=7687`、`DB_DISPLAY_NAMES` |
| 内置类型 | `core/db_adapters.py` | `BUILTIN_TYPES` 含 neo4j（不允许被自定义适配器占用同名） |
| 探测 | `core/probe.py` | `_PROBES["neo4j"]` |
| 产物格式 | `core/dump_format.py` | 5 种通道 + 扩展名 + **每种都有真实恢复方式** |
| 接口 | `api/tasks.py` | `_LIST_DB_SKIP` 排除 `system` 系统库；无 JDBC/原生通道的类型不再被判成故障 |
| 前端 | `templates/tasks.html`、`static/js/app.js` | 类型下拉新增 Neo4j；逻辑-only 类型**自动禁用「物理备份」**并 toast 提示；新建任务预填默认端口 |

### 1.4 契约测试

`tests/test_neo4j_registration.py`（7 组断言，把"新增一种库要改哪些地方"固化下来）：config 类型/端口/显示名 → 引擎注册表与能力声明 → dump_format 五通道默认项与真实恢复方式 → probe 注册与入参诚实 → BUILTIN_TYPES → 物理备份被诚实拒绝 → 前端下拉与后端格式表一致。

### 1.5 已知边界

- 社区版**在线**备份只能走 APOC 通道（需装 APOC 并开启 `apoc.export.file.enabled`），否则必须停库 dump。
- `backup` 通道在企业版之外的环境执行会失败，平台自动回退离线 dump 并在日志中说明。
- 尚未在真实 Neo4j 实例上做端到端备份/恢复验证（本机无 Neo4j 环境），后续补测。

## 二、虚拟机备份子系统（core/vm，新增 · **尚未做真实环境实测**）

> **⚠️ 状态说明（按本次要求备注）：本模块已完成架构设计、数据模型、四种 Provider 接入、API 与页面，并通过契约测试；但因为没有可用的虚拟化环境（PVE / ESXi / Hyper-V / libvirt 宿主机），未做端到端真实备份与恢复验证。请待有环境后再行测试优化，暂不建议在生产使用。**

### 2.1 设计取向：不新建平行调度体系

把「虚拟机」伪装成一种**受保护对象**，复用平台既有的任务调度、备份记录、备份集链、三级存储、生命周期与告警：

- 每台受保护 VM 对应一条 `backup_tasks(db_type='vm')` → 调度、保留策略、告警全部走既有链路；
- 恢复点（PIT）单独建链（`vm_recovery_points`，全量 / 增量 / 合成全量），支持按时间点还原；
- 引擎 `VMBackupEngine` 通过 `_register_vm_engine()` **惰性注册**——`core.vm.engine` 依赖 `core.engines.base`，顶层 import 会与 `core.engines.__init__` 循环导入，改为运行时按需绑定。

### 2.2 数据模型（4 张表，全部加索引）

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `vm_hypervisors` | 纳管的虚拟化平台 | provider / endpoint / 账号密码或 API Token（`db.encrypt_secret` 加密）/ verify_ssl / extra_config |
| `vm_protected` | 受保护虚拟机 | `vm_ref`（PVE:vmid / libvirt:UUID / ESXi:vmid / Hyper-V:VMId）、`task_id`、备份间隔、一致性级别、`rpo_target_min`、`last_change_token` |
| `vm_recovery_points` | 恢复点（PIT） | `rp_type`（full/incremental/synthetic_full）、`parent_rp_id`、`change_token` / `parent_token`、`artifact_path`、`verified` |
| `vm_jobs` | 作业 | `mode`（restore_in_place / clone / verify / delete）、`isolate_network`、`auto_start`、`ttl_hours`（到期自动销毁演练 VM） |

### 2.3 平台支持矩阵

| 虚拟化平台 | 接入方式 | 备份通道 | 增量能力 | 克隆新 VM |
| --- | --- | --- | --- | --- |
| Proxmox VE | HTTPS API（账号密码 / API Token） | `vzdump`；PBS 存储时走 PBS 备份 | 备份存储为 PBS 时支持块级增量，否则按全量执行（**如实说明，不伪造增量**） | 支持（隔离网络、改 MAC、自动开机、TTL 销毁） |
| KVM / libvirt | SSH + `virsh` | 快照/检查点 + 磁盘镜像导出 | `virsh backup-begin` 可用时支持真块级增量（dirty bitmap），否则回退全量 | 支持 |
| VMware ESXi | SSH + `vim-cmd` | 关机/快照后打包 VM 目录（vmdk） | 依赖快照链，不支持时回退全量 | 支持 |
| Microsoft Hyper-V | SSH + PowerShell | `Export-VM` / 检查点导出（VSS 应用一致） | 依赖检查点，不支持时回退全量 | 支持 |

全部走 SSH/HTTPS 远程通道，**虚拟化平台侧零安装、零 agent**（与平台"客户端零安装"原则一致）。

### 2.4 核心能力

1. **恢复点链（journal）**——刻意做成纯函数式的时间/数据库运算（不碰网络、不碰 Hypervisor），便于单测：
   - `plan_next()`：下一次该做全量还是增量（Veeam 永久增量 + 周期性合成全量思路）；
   - `resolve_chain()` / `chain_artifacts()`：恢复到某个时间点需要哪些产物；
   - `find_rp_by_time()`：时间点 → 恢复点；
   - `current_rpo_minutes()` / `rpo_state()`：当前 RPO 与**偏离 RPO 目标**判定（Rubrik SLA Domain 思路）。
2. **合成全量（synthetic full）**：在**备份仓库侧**把增量链合成一份新全量，获得全量恢复速度又不占生产 IOPS。
3. **自动恢复验证（verify）**——对应 Veeam SureBackup：**在隔离网络里真正拉起一台 VM**，执行真实健康检查（心跳 / ICMP / TCP 端口 / HTTP / 自定义脚本），确认「这份备份可用」后销毁验证 VM。所有检查都是真实动作，**不允许默认通过**：拿不到 IP、ping 不通、端口不通、脚本非零退出码一律判失败并写清原因。
4. **克隆 / 原地还原 / 即时恢复**：`isolate_network`（隔离网络防 IP 冲突）、`auto_start`、`ttl_hours`（演练克隆到期自动销毁）。
5. **RPO 报告**：按 VM 给出当前 RPO 与目标 RPO 的对比，超限可对接既有告警。

### 2.5 接口与页面

- `api/vm.py`（约 20 个端点）：providers / hypervisors(CRUD + test + discover vms) / protect / protected(CRUD + backup) / recovery-points / restore / clone / verify / jobs / rpo-report / plan-report。
- `templates/vm.html` + `static/js/vm.js`（400 行）：四个标签页——虚拟化平台、受保护虚拟机、恢复点、作业/验证；纳管弹窗支持账号密码与 API Token 两种凭据、测试连接、VM 发现与能力提示。

### 2.6 契约测试

`tests/test_vm_backup.py`（不需要真实虚拟化平台，用不可达地址 `127.0.0.1:1` 验证失败路径）：

1. `get_engine('vm')` **必须**拿得到引擎（惰性注册一旦失效，调度/备份/还原/克隆/验证会全线报「不支持的数据库类型」）；
2. 四种 Provider 均已注册且能给出**静态能力声明**（不支持块级增量时必须如实说明，不允许伪造增量）；
3. `journal.plan_next` / `rpo_state` 纯逻辑正确性（无真实环境也能验证"不造假"）；
4. 表结构可用；不可达时**诚实失败**而非假成功。

### 2.7 后续测试优化计划（待环境）

- [ ] 在 PVE 上做真实 `vzdump` 备份 → 恢复点 → 原地还原 / 克隆新 VM / 自动恢复验证全链路；

## 七、首页（仪表盘）态势化改造 · 对标 Veeam / Commvault / Rubrik

### 7.1 结论（先说问题）

原首页是**"数量统计页"**：任务数、记录数、总大小、健康分 + 两个分布饼图。对标业界（Veeam Home 的 Protected/Overdue/Restore points、Commvault Command Center 的 SLA compliance、Rubrik 的 Incompliance、Cohesity 的 Capacity forecast）缺的是**风险与合规视角**——"有多少数据真的被保护住了"和"哪些已经逾期"。本轮按这个方向补。

### 7.2 已实现（逐项，附验证方式）

### 7.3 健康评分重构（修掉两个真实缺陷）

维度由「任务覆盖30 + 成功率40 + 调度20 + 同步延迟10」改为「**保护覆盖25 + 成功率30 + 调度15 + RPO合规20 + 时效10**」。

- **修虚指标**：旧"任务覆盖 30 分"只要存在任务就恒满分，毫无区分度 → 换成保护覆盖（真有成功备份的比例）。
- **修时区 bug**：库里时间是 `2026-09-16T19:40:48+08:00`（带偏移本地时间），旧代码用 `datetime.utcnow()` 相减 → 东八区**恒定偏差 8 小时**。改为 aware 时间比较。
- 结果：评分从虚高的 **89 降到真实的 64**（真实原因是 37 个启用任务里 36 个已长期未备份，多指向已关机的 133/139 主机）。

### 7.4 顺带修掉的分层复制缺陷

物理备份产物是**目录**（xtrabackup 备份集），被当单文件读 → `IsADirectoryError`，带重试的调度任务**每 30 秒刷一条 ERROR**。改为先 tar.gz 打包再复制（`core/tier_replication.py`），临时包用完即删。实测：L1-MinIO / L2-S3 / L3-Local / D2T-磁带 四层全部成功（1.9MB），日志再无该 ERROR。

### 7.5 口径说明（这几项容易被误读，如实标注）

1. **"恢复点 1612 个" = 成功备份记录条数**，**没有**逐条校验产物文件是否仍存在于磁盘（可能已被保留策略清理）。要严谨需加产物存在性校验，本轮未做。

4. **保护粒度是"任务级"**，不是"实例/库级"——一个任务覆盖多库时不体现。

### 8.2 修复的缺陷（6 个）

1. **自增属性丢失**（`core/sync/plugins/mysql.py`）：MySQL/MariaDB 源的自增只存在于 `INFORMATION_SCHEMA.EXTRA`，`COLUMN_DEFAULT` 为 NULL，目标表因此丢自增，后续写入主键冲突。改为读取 EXTRA 并在目标 DDL 还原 `AUTO_INCREMENT`；自增列非主键时补 `UNIQUE KEY`（MySQL 要求自增列必须是键）。
2. **PG → MySQL 整表建表失败**：PG serial 的默认值 `nextval('t_types_id_seq'::regclass)` 被直接拼进 MySQL DDL，`CREATE TABLE` 报 1064 → 整表跳过。新增 `_mysql_default()`：序列默认值转自增、函数默认值转 MySQL 写法、`'x'::type` 字面量剥除类型转换、无法换算的原生表达式**不生成 DEFAULT**（宁可缺默认值，也不能让整表建不起来）。
3. **时间默认值精度**：`DATETIME(6) DEFAULT CURRENT_TIMESTAMP` 报 1067 `Invalid default value`。改为默认值表达式与列精度一致（`CURRENT_TIMESTAMP(6)`）。
4. **跨源类型名归一化缺失**：PG 的 `CHARACTER VARYING` 取首词成 `CHARACTER`，匹配不到任何标准分支而落到兜底 `TEXT`，`varchar(50)/(100)` 长度全部丢失。新增异源类型名归一化表（`CHARACTER VARYING`→`VARCHAR`、`NUMERIC`→`DECIMAL`、`DOUBLE PRECISION`→`DOUBLE`、`BOOLEAN`→`TINYINT`、带/不带时区时间戳→`DATETIME` 等）。
5. **"假成功"掩盖失败**（`core/sync/engine.py`）：全库迁移只看行级错误数，整表建表失败时"读 0 写 0 错误 0"被判成功，直到校验阶段才抛出难定位的错误。改为有失败表一律判失败。
6. **列元数据契约**（`core/sync/plugins/base.py`）：`ColumnMeta.is_primary` / `auto_increment` 原先靠动态属性在插件间传递，正规化为字段。

### 8.3 目标侧保真核验（MySQL 目标实测）
